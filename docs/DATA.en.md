# Data, Evidence, and Demonstration Sets

[简体中文](DATA.md) · English

This document describes the data organization, runtime boundaries, and demonstration data in the current delivery. See [`data/README.md`](../data/README.md) for the data-directory entry point. All demonstration suppliers, materials, quotations, policy documents, and purchasing history are synthetic.

## 1. Directory responsibilities

```text
data/
├── contracts/                  Field dictionaries, schemas, and interface contracts
├── policies/                   Publishable procurement policies and set manifests
├── examples/policy_rag/        Minimal Policy RAG example
├── source/                     Upstream source data, licenses, and provenance notes
└── generated/
    ├── demos/                  Current manually runnable demonstration packages
    ├── fixtures/extraction/    Parser-boundary and format-test fixtures
    ├── fixtures/compliance/    Compliance-verification fixtures
    └── supplier_history/       Deterministically generated supplier-history releases

evaluation/
└── reference/                  Reference answers and offline acceptance data
```

`data/generated/demos/` may be used as user-upload input. `evaluation/reference/` is for test programs and acceptance reviewers only and must not be uploaded or mounted for the runtime agent.

## 2. Quotation field contract

Quotation review fields are defined by `data/contracts/quote_data_field.csv` and backend endpoint `GET /api/v1/quote-field-schema`; the frontend does not maintain a duplicate field table. Current coverage is:

| Group | Fields |
| --- | --- |
| Identity | `supplier_name`, `supplier_country` |
| Specification | `category`, `item`, `manufacturer`, `manufacturer_part_number`, `package`, `revision`, `condition` |
| Price | `currency`, `unit_price`, `price_basis_quantity`, `price_basis_unit` |
| Packaging | `packaging_type`, `units_per_pack`, `order_multiple_units` |
| MOQ | `moq_quantity`, `moq_unit` |
| Fees | `shipping_fee_status`, `shipping_fee_amount`, `other_fees_status`, `other_fees_amount`, `tax_mode` |
| Delivery | `lead_time_days`, `day_basis`, `delivery_semantics`, `start_event` |
| Commercial | `payment_terms`, `quote_date`, `valid_until` |

Each candidate field includes at least its raw value, normalized value, unit, validation status, source citations, and adapter/prompt version. Business IDs and quotation versions are generated or validated by the backend and must not trust model-provided values.

### Status and origin

| Dimension | Value | Meaning |
| --- | --- | --- |
| `validation_status` | `EXTRACTED` | Extracted but not yet eligible for deterministic verification |
|  | `VERIFIED` | Passed structural, range, unit, and evidence validation |
|  | `MISSING` | Not present in the source or not reliably identifiable |
|  | `CONFLICT` | Conflicting candidates exist for the same field |
| `origin` | `DOCUMENT` | From the uploaded original |
|  | `USER_INPUT` | A new fact supplied by the user |
|  | `USER_CORRECTION` | A user correction to parser or model output |
|  | `DERIVED` | Calculated from confirmed inputs using an explicit rule |

Fee status is `KNOWN_AMOUNT | FREE | INCLUDED | NOT_APPLICABLE | UNKNOWN`. An `UNKNOWN` amount must be empty rather than zero. Monetary values use decimal strings. Package quantity, order multiple, and MOQ are three separate concepts.

## 3. Files and evidence

- PDF evidence includes file/quotation version, hash, page, stable text-block ID, source excerpt, and coordinates when available.
- CSV evidence includes file/quotation version, hash, row number, and column name.
- A model may cite only source IDs generated by the current extraction and belonging to the correct file version.
- Human corrections preserve the original extracted value; derived values record their input fields and rule version.
- Replacing a file creates a new version. Previous files and citations remain available to historical snapshots.

## 4. Policies and compliance evidence

Policy data has three layers:

1. Original policy files and scope metadata;
2. Human-reviewed clauses, control codes, and executable parameters;
3. Published embedding indexes and version manifests.

Supplier evidence is task-level and supplier-level versioned evidence. The current closed loop supports supplier admission, RoHS compliance, and amount-approval controls. Parsers assist with evidence-fact extraction, but users must review and confirm the facts. A compliance assessment freezes its policy citations, evidence citations, evaluation time, and deterministic status together.

## 5. Current end-to-end demonstration: full_flow_demo4

Entry point: `data/generated/demos/full_flow_demo4/`.

The data set includes:

- One procurement requirement and a confirmation reference;
- A primary Electronics/SG policy and a negative policy with a mismatched scope;
- PDF and equivalent CSV quotations for four suppliers;
- Initial supplier-admission/RoHS evidence and three replacement documents;
- Isolated variants for missing freight, conflicting prices, wrong part number, MOQ, ties, and prompt injection;
- Binding metadata for the synthetic supplier-history release `2026-08-06-v1`.

The fixed evaluation date for the primary scenario is 2026-11-02. PDF and CSV are equivalent input paths and must not be mixed within one task. Each `variants/` case must use a new task and replace only the single supplier quotation specified by its manifest.

See [TESTING.en.md](TESTING.en.md) for the complete manual procedure and the package `README.md` for the upload order. Offline expected results live in `evaluation/reference/full_flow_demo4/` and must not be exposed to the runtime agent.

## 6. Supplier history

Runtime history releases live under `data/generated/supplier_history/mcu9/{dataset_version}/` and are deterministically generated from `data/source/purchase_orders.csv`. A release contains its content hash, manifest hash, statistics period, sample threshold, rating-method version, and synthetic-data marker.

Tasks pin a concrete version through `task_history_bindings`. Historical results must read their frozen snapshot and must not be backfilled with newer supplier-history data.

## 7. Data maintenance rules

- Put new user-facing demonstration packages under `generated/demos/` and focused boundary cases under `generated/fixtures/`.
- Do not duplicate entire data sets using names such as `quote_V1` or `quote_V2`.
- Generated data must have a reproducible generator, fixed seed or content hash, and an explicit synthetic-data marker.
- Keep development, calibration, and holdout sets separate. Once a holdout sample is used for debugging, it no longer qualifies as a final holdout sample.
- Reference answers, simulated responses, and unredacted ground truth must not enter runtime directories.
- After changing generated files, update file sizes and hashes in the manifest or rebuild them with the corresponding generator.
