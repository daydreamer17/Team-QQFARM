# 决策助手事实校验修复记录

日期：2026-09-21；对话提示词版本：`decision-conversation/1.5.0`。

## 问题与修复

`factual statement is missing an inline reference` 是应用层校验错误，不是 Worker 没有启动。旧输出把报价事实、用户偏好和澄清问题混在同一段文字中；关键词校验会把对话措辞当成必须引用的报价事实。只重启不会改变这种输出契约冲突。

- `assistant_text` 只承载有引用的冻结事实；`changes` 承载待确认的结构化变更；新增 `clarification` 承载有限的澄清类型。服务端渲染确认/澄清文案，纯变更不必伪造事实和引用。
- “必须当天收到”先澄清。最晚到货日允许提前到货，不代表精确配送日期；不自动将两者等同。
- 加入冻结 `REQUIREMENT` 引用，区分已确认需求与报价结果。用户聊天内容不能替代已确认事实。
- 紧跟句号后的显式引用可关联到前一句；仍不能用回答末尾的全局引用列表掩盖无引用事实。
- 模型生成和持久化两层校验都保留；持久化校验包含当前用户消息上下文。
- 当前偏好与新提议相同时正常说明“无需生成新情景”，不再把无变化视为聊天失败。
- 失败 Job 保存有界校验诊断，用户气泡保留简明错误，不输出凭据或完整模型请求。

## 本地复验

加载更新后的 API 与 Worker 代码后，在当前有效结果的新对话中分别发送：

1. “我就想在10月18号那天收到货，我就那天有时间”：应澄清最晚到货与精确当天配送的区别，不直接生成截止日期变更。
2. “我想要成本最低”：应说明当前成本结论或提出排序变更；若已经是该偏好，不生成无意义的新情景。
3. “改成最快到货优先”：当与当前偏好不同，应出现待确认变更，确认后生成 Scenario；正式应用仍单独确认。

旧失败消息保留历史，不会因代码更新自动变成成功。若显示规则版本不匹配，需要先重新运行分析；这与本次引用校验错误是两个不同问题。
