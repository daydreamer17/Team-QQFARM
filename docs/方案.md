结合你们 **Python 后端＋React 前端、四人团队、约 120 小时、AWS 权限尚未确认** 的情况，我建议优先考虑这套组合：

**固定规格包装盒＋FastAPI／React＋Strands＋PostgreSQL＋pdfplumber＋单机 Docker 部署。** 模型先用比赛账号可调用的 Sonnet 候选建立质量基线，再比较便宜模型。

以下排序针对你们这次比赛。**难度 1–5，越低越容易；适配度 1–5，越高越符合当前项目。** 分数是工程判断，不是实测结果；主办方指定环境的优先级高于这些排序。

**1. 商品类别：优先延续包装盒，减少重新设计样例的工作**

| 排名  | 可选项                     | 难度 | 适配度 | 主要取舍                                                    |
| ----- | -------------------------- | ---- | ------ | ----------------------------------------------------------- |
| **1** | **固定规格的无印刷包装盒** | 2    | 5      | 能自然展示按箱／按个、MOQ、运费和交期；已有演示案例可以复用 |
| 2     | 固定规格 A4 打印纸         | 1    | 4      | 规格和包装容易标准化，最容易跑通；演示的差异性稍弱          |
| 3     | 固定型号的办公外设，如键盘 | 3    | 3      | 商品容易理解，但型号、保修、配件和替代品会增加比较规则      |

**建议选包装盒，但固定一张规格表**，明确尺寸口径、材质、结构、是否印刷等。首版按这些字段核对，不让模型自由推断两个描述不同的商品“质量差不多”。

报价之间的变化集中在价格、包装数量、MOQ、费用、交期和付款条件，方便建立可靠参考答案。

**2. 应用技术栈：FastAPI＋React 最适合你们现有经验**

| 排名  | 可选项                       | 难度 | 适配度 | 主要取舍                                                     |
| ----- | ---------------------------- | ---- | ------ | ------------------------------------------------------------ |
| **1** | **FastAPI＋Pydantic＋React** | 2    | 5      | 能沿用团队技能；接口、结构化数据和前后端分工清楚             |
| 2     | Django＋React                | 3    | 4      | 用户、权限和后台管理较完整；如果团队没有 Django 经验，学习成本更高 |
| 3     | Streamlit＋Python 业务模块   | 1    | 3      | 最快形成原型；复杂来源查看、版本变化和审批交互需要更多定制   |

FastAPI 的类型化请求和校验能力适合你们的字段契约，但业务规则仍需要自行实现。[FastAPI 官方文档](https://fastapi.tiangolo.com/)

**具体建议：**React 做比较表、来源面板和补问表单；FastAPI 承担状态、计算和审批。前端采用已有熟悉的组件库，首版不专门开发设计系统。

**3. Agent 框架：Strands 第一，熟悉 LangGraph 时可交换顺序**

| 排名  | 可选项                      | 难度 | 适配度 | 主要取舍                                                     |
| ----- | --------------------------- | ---- | ------ | ------------------------------------------------------------ |
| **1** | **Strands＋后端业务状态机** | 2    | 5      | 适合一个 Agent 调用工具的方案，与 Bedrock 路线衔接自然       |
| 2     | LangGraph＋Bedrock          | 3    | 5      | 显式分支、暂停和恢复表达清楚；图状态与业务状态的边界要设计好 |
| 3     | Amazon Bedrock Agents       | 3–4  | 3      | 可采用 AWS 托管编排，但需要额外配置服务、权限和应用集成      |

Strands 已提供会话持久化；LangGraph 也提供中断、检查点和恢复机制。它们都不能自动替代你们的采购版本与审批事务。[Strands 会话管理](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/)、[LangGraph 中断机制](https://docs.langchain.com/oss/python/langgraph/interrupts/)

**排序调整条件：**

- 如果已有队员做过 LangGraph 的持久化补问，**LangGraph 升为第一**。
- 如果主办方提供某框架的可运行模板，优先复用模板。
- 首版只选一个 Agent 框架，避免同时引入 Strands 和 LangGraph，形成两套恢复机制。

Amazon Bedrock Agents 是独立的托管 Agent 能力，不等同于“在 Bedrock 上调用模型”。选择它会影响整体集成方式。[AWS 官方说明](https://docs.aws.amazon.com/bedrock/latest/userguide/agents.html)

**4. 模型：先排验证顺序，再根据你们的数据决定最终选择**

模型尚未在你们的报价集上测试，下面是**候选验证顺序，不是准确率排行榜**。

| 顺序  | 候选项                                            | 集成难度 | 推荐用途                     | 决定是否采用的依据                       |
| ----- | ------------------------------------------------- | -------- | ---------------------------- | ---------------------------------------- |
| **1** | **Claude Sonnet 4.6，或账号内获准的 Sonnet 版本** | 2        | 首轮质量基线、条款理解和补问 | 关键字段、引用和工具调用能否稳定通过     |
| 2     | Claude Haiku 4.5                                  | 2        | 提速和降低调用成本的候选     | 相比基线，是否增加错误修正或补问负担     |
| 3     | Amazon Nova 2 Lite                                | 2–3      | AWS 模型候选、文档处理对照   | 账号可用性，以及同一测试集上的质量和成本 |

AWS 官方资料列出了上述模型；Nova 2 Lite 的定位包括文档处理和简单自动化。但 **AWS 已提供不等于比赛账号已授权**，可用区域、推理方式和配额都需要实测确认。[Sonnet 4.6](https://docs.aws.amazon.com/en_en/bedrock/latest/userguide/model-card-anthropic-claude-sonnet-4-6.html)、[Haiku 4.5](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-haiku-4-5.html)、[Nova 2 Lite](https://docs.aws.amazon.com/en_en/bedrock/latest/userguide/model-card-amazon-nova-2-lite.html)

**建议选择办法：**从开发集取 6–8 个案例，覆盖包装单位、缺运费、交期歧义和报价更新。比较：

- 关键字段与来源正确性；
- 工具调用成功率；
- 人工纠正次数；
- 整个任务耗时和总调用成本。

首版先用一个模型完成闭环。只有实测证明收益明显，再把简单提取交给便宜模型；这样可以控制提示词和回归测试的数量。

**5. PDF 解析：pdfplumber 第一，暂时保留文本 PDF 的范围**

| 排名  | 可选项                        | 难度 | 适配度 | 主要取舍                                             |
| ----- | ----------------------------- | ---- | ------ | ---------------------------------------------------- |
| **1** | **pdfplumber＋LLM 字段理解**  | 2    | 5      | 能获取文本、表格及位置数据，适合来源定位和报价表     |
| 2     | pypdf＋LLM 字段理解           | 1–2  | 4      | 简单文本提取容易；复杂表格和精细定位需要更多处理     |
| 3     | Amazon Textract＋LLM 字段理解 | 3    | 3      | 适合扩展 OCR／表格处理，但增加云权限、调用和费用依赖 |

pdfplumber 提供文本、表格和页面对象信息；pypdf 本身不提供 OCR；Textract 则提供结构化表格分析能力。[pdfplumber](https://github.com/jsvine/pdfplumber)、[pypdf](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)、[Textract 表格分析](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-tables.html)

**建议首版约束：**

- PDF 每份最多 **5 页、5 MB**，单任务最多 **5 份**；这是建议的应用限制，需要按样例验证。
- CSV 固定字段模板，每行一份供应商对该商品的报价。
- 先由解析器生成页码、文本块 ID 和原文，再交给模型识别字段。
- 扫描件提示更换文件或人工录入，暂不增加 OCR 分支。

**6. 数据库和后台任务：PostgreSQL 更贴合审批与版本需求**

| 排名  | 可选项                                  | 难度 | 适配度 | 主要取舍                                                     |
| ----- | --------------------------------------- | ---- | ------ | ------------------------------------------------------------ |
| **1** | **PostgreSQL＋数据库作业表＋单 worker** | 3    | 5      | 适合事务、版本检查和并发写入；多一个数据库服务需要维护       |
| 2     | SQLite＋数据库作业表＋单 worker         | 1–2  | 4      | 部署轻便，足以支撑受控演示；需要严格限制并发写入             |
| 3     | DynamoDB＋条件写入／事务                | 4    | 3      | AWS 托管方向可行，但任务、版本、审批和报告查询需要另一套建模方式 |

PostgreSQL 有行级锁等并发控制能力；SQLite 也支持事务，但同一数据库文件同时只能有一个写入者。**SQLite 能实现正确审批，并非必须换 PostgreSQL 才安全。** 这里把 PostgreSQL 排第一，是因为更贴合你们已经写下的并发与版本需求。[PostgreSQL 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)、[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

建议：

- 有人熟悉 Docker／PostgreSQL：从第一天就用 PostgreSQL。
- 无人熟悉数据库运维，而且只部署单实例：SQLite 可以升为第一。
- 无论哪种，采用短事务领取任务，释放事务后再调用模型；不要在等待模型时持续持有数据库写锁。
- 暂不增加 Redis＋Celery。先把作业表、有限重试、版本检查和单 worker 做完整。

**7. AWS 部署与文件存储：先复用比赛环境，再考虑自由选型**

如果主办方没有指定部署平台，我建议：

| 排名  | 可选项                         | 难度 | 适配度 | 主要取舍                                                     |
| ----- | ------------------------------ | ---- | ------ | ------------------------------------------------------------ |
| **1** | **EC2＋Docker Compose**        | 3    | 5      | 应用、worker、数据库部署方式直观；需要处理 HTTPS、备份和实例运维 |
| 2     | Lightsail 实例＋Docker Compose | 2–3  | 4      | 单机部署简便；调用 Bedrock／S3 的凭据供给方式需先验证        |
| 3     | ECS Fargate＋外部数据库        | 4    | 3      | 托管容器方向清楚，但网络、角色、服务和数据库集成增加工作量   |

**如果比赛直接提供可用的 Lightsail 实例和模型访问方式，Lightsail 应升为第一。**

EC2 的一个具体优势是可以通过实例 IAM role 为应用提供临时 AWS 凭据；Fargate 可以免去底层服务器管理，但仍需要配置容器应用相关基础设施。[EC2 IAM role](https://docs.aws.amazon.com/us_en/AWSEC2/latest/UserGuide/attach-iam-role.html)、[Fargate 官方说明](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/AWS_Fargate.html)

文件存储的顺序可以单独确定：

| 排名  | 方案                           | 难度 | 适用情况                                        |
| ----- | ------------------------------ | ---- | ----------------------------------------------- |
| **1** | **私有 S3 存储原始报价和报告** | 2    | 比赛账号允许创建或使用 bucket，部署应用可以访问 |
| 2     | 单实例持久化磁盘目录           | 1    | S3 权限未开放，先完成单机演示；需要备份         |
| 3     | Lightsail 对象存储             | 2    | 主办方已提供对应资源和访问配置                  |

本地方案必须使用持久化目录／卷，避免把唯一文件副本放进可随部署替换的容器文件层。数据库保存文件 ID、哈希和位置，业务版本仍由应用管理。

**8. 登录、数据来源及运行限制：采用最小但真实的实现**

认证方案建议这样排序：

| 排名  | 方案                                       | 难度 | 适配度 | 主要取舍                                     |
| ----- | ------------------------------------------ | ---- | ------ | -------------------------------------------- |
| **1** | **预建具名账户＋成熟认证组件＋服务端会话** | 2–3  | 5      | 满足队员和评委演示；省去注册、找回密码等流程 |
| 2     | Cognito managed login                      | 3    | 4      | 托管登录；需要账号权限和登录回调配置         |
| 3     | 复用学校／企业 OIDC 登录                   | 3–4  | 3      | 有现成配置时很好，否则依赖组织管理员         |

第一种方案只保留采购用户和审核人两类权限，**角色由后端保存，不通过前端下拉框随意切换**。密码哈希和会话处理复用成熟组件。如果主办方提供了 Cognito 模板，第二项升为第一。Cognito 确实提供托管登录页面，但业务审批权限仍需应用检查。[Cognito managed login](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-managed-login.html)

数据来源则建议：

1. **团队制作虚构报价＋人工参考答案**：实现最容易、可公开演示、异常可控，作为必备基础。
2. **获授权的匿名化真实报价**：用于验证真实版式，提高业务说服力；有数据时补充。
3. **直接使用真实企业完整报价**：对当前 MVP 的额外收益有限，展示和保留范围也更难管理，暂不优先。

运行限制不必长期悬而未决，可以先采用可配置初值：**单任务一个活跃执行、每阶段最多 3 次尝试、单次 Agent 运行最多 8 次模型调用**。超时根据开发样例的实际延迟调整；业务字段缺失直接补问，不通过重试猜答案。

今天可以先确定商品、FastAPI／React、解析器、数据库和数据模板。向主办方集中确认四项即可：**允许的框架、可调用模型与区域、部署服务及应用凭据方式、额度与资源有效期**。这四项确定后，就能把以上条件排序收敛成最终技术选型。
