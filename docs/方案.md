**3. Agent 框架：已选择 LangGraph，显式编排单一采购比选流程**

采用 **LangGraph＋后端业务模块＋PostgreSQL 持久化检查点**。首版使用一个主图，将文档理解、补问和推荐解释放在模型节点，将规格校验、单位换算、成本计算及版本检查放在确定性业务模块中，由图节点调用；节点不等于独立 Agent，首版不增加多 Agent 协作。[LangGraph 概览](https://docs.langchain.com/oss/python/langgraph/overview)

| 阶段 | 职责与路由 |
| ---- | ---------- |
| 读取输入与解析 | 校验当前任务版本，加载报价文件；pdfplumber／CSV 解析器生成原文与稳定来源 ID |
| 字段理解 | 模型提取料号、封装、价格和条款并关联来源，经 Pydantic 与证据校验后保存 |
| 业务校验与补问 | 判断规格、数量和费用是否满足比较条件；存在影响推荐的待确认问题时，组织问题并通过 interrupt 暂停，回答后回到校验阶段 |
| 确定性比较 | 信息满足计算条件后调用独立 Python 模块，计算采购量、成本、可行性和排序；所有在范围内报价均确认不可行时返回 NO_FEASIBLE_OPTION |
| 制度检索 | retrieve_policy 根据当前问题／规则原因码，在任务绑定的制度版本与范围内检索相关条款，记录检索轨迹 |
| 推荐解释与结束 | explain_with_sources 基于计算结果和检索条款生成解释，区分报价事实与制度依据；后端核验引用及当前版本后保存可审核结果，结束图运行 |
| 人工审批 | React 通过 FastAPI 审批接口提交，由后端事务校验权限、版本、阻塞问题和有效期；首版审批独立于图执行 |

**状态与持久化边界：**PostgreSQL 业务表是任务、报价、问题、结果和审批的权威记录；LangGraph 检查点保存执行位置和图上下文。检查点使用 PostgresSaver／AsyncPostgresSaver 等持久化实现，可与业务表共用数据库服务，但使用独立表并管理其初始化与版本。数据库作业表负责调度、租约和重试，检查点负责图恢复，两者职责不同。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)

**补问、恢复与报价更新约束：**

- 以独立的 graph_run_id／thread_id 标识一次逻辑图运行，记录它与 task_id、输入版本、待补问题及作业的关联；不直接用 task_id 作为所有版本共用的恢复标识。
- 补问问题幂等保存到业务表后触发 interrupt，检查点持久化后释放 worker。前端通过业务接口读取问题，不保持 HTTP 请求或数据库事务等待用户。
- 用户回答需通过问题 ID、关联运行和预期任务版本校验。在同一业务事务内保存回答、推进 task_revision 并创建恢复作业，记录回答前后的版本对应关系；恢复调用以已保存回答的引用作为输入，不能信任前端直接传入的图状态。
- 恢复作业只恢复关联的待补中断。恢复后重新读取已确认业务数据，更新图中的输入版本，生成新输入快照并执行完整业务校验和重算；不继续使用补问前的比较结果。若回答提交后又发生其他修改，则拒绝过期恢复。
- 上传新报价、修改需求、主动修正字段或调整比较范围时，旧图运行失效，并为新输入版本创建新图运行；旧检查点保留追溯，迟到结果不得写成当前结果。上述已校验补问回答是受控恢复入口。
- interrupt 恢复会重新执行所在节点开头的代码，节点写入必须幂等。检查点写入与业务事务不假定原子提交；通过运行／问题／作业 ID、状态核对和有限重试恢复中断窗口。若尚无匹配的持久化中断，恢复作业不得盲目发送 resume。[LangGraph 中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts/)
- 按任务串行推进图执行，单次逻辑图运行最多 8 次模型调用，作为可配置初值，按开发样例调整；恢复和重试沿用同一逻辑运行的调用计数，不能通过新增作业重置模型预算。超时按实测延迟配置，业务字段缺失直接补问，不通过重试猜答案。
- 模型适配器统一管理本地开发 API 与 AWS 部署测试 API 的接入，按第 4 节配置切换；具体协议、模型、区域及认证方式以实际接口为准。

**5. PDF 解析：已选择 pdfplumber＋LLM 字段理解**

首版处理英文、可提取文本的 PDF。pdfplumber 负责提取文字、表格及位置；应用解析层据此生成页码、稳定文本块 ID 和原文记录；LLM 负责理解料号、封装、价格、MOQ、运费和交期等业务字段。pdfplumber 主要适用于机器生成的 PDF，本身不提供 OCR。[pdfplumber 官方说明](https://github.com/jsvine/pdfplumber)

处理链路：**上传文件→pdfplumber 解析→LLM 提取字段并关联来源→Pydantic／证据与业务校验→必要时补问→确定性比较→制度检索→带引用解释**，由 LangGraph 编排。

**5.1 采购制度 RAG：正式必交付模块**

- 知识库：团队编写 3–5 份简短英文 Markdown 制度，覆盖报价完整性、采购比较、审批变更和 Electronics 同规格要求，全部标记为演示用虚构制度。它们独立于报价 CSV／PDF，也不包含主场景金额、供应商答案或隐藏评测资料。
- 检索：按章节形成稳定条款 ID，PostgreSQL 保存版本、范围、生效时间、哈希和条款正文。后端先过滤任务绑定的有效制度集合，再用 BM25 检索，Top-3 为可配置初值；复用轻量库，固定分词和检索版本。第一版英文制度与英文查询，界面按钮可显示中文并映射为固定英文查询；任意跨语言问答不在首版承诺内。
- 集成：LangGraph 增加 retrieve_policy 和 explain_with_sources，解释覆盖缺失信息、推荐和报价变更原因。React 与 HTML 报告展示文档标题、版本、章节、引用原文和检索状态；无需另建聊天产品或独立 Agent。
- 权限：检索只解释已确认事实和既定业务规则，不能补出本次报价的未知费用、改变排序或批准采购。无依据、语义不支持或条款冲突时明确说明；检索失败可保留确定性结果，但不得宣称制度引用成功或自动合规。
- 版本：任务绑定 policy_set_version，快照与解释保存相应版本和检索轨迹。发布知识库新版本不回写旧任务；显式切换任务制度集合时推进修订、重算、使旧推荐／审批失效。制度规则若与代码不一致，先修正文档／规则并重新评审，不由模型裁决。
- 验收：A 准备制度与独立问题参考，B 负责检索及引用生成，C 验证规则一致性与云端运行，D 负责版本／图集成及展示契约；第二周正式分配 10 个团队工时，计入原有 32 小时计划，详见项目计划第 5.3 节。RAG 失败路径可降级运行，但正式交付仍必须通过 RAG 验收。

RAG 不要求向量数据库，可直接使用已有数据源构成检索增强流程。[LangChain 检索说明](https://docs.langchain.com/oss/python/langchain/retrieval)。向量检索、重排和自主多轮检索不属于本次首版范围。

**PDF 来源与生成约定：**

- 所选 Procurement Spend Analysis Dashboard 提供合成历史采购订单 CSV，演示报价 PDF 由团队基于 Electronics／MCU-9 数据生成，不作为原始供应商报价。[数据集说明](https://github.com/dytcoke23/procurement-spend-analysis-dashboard#the-dataset)
- 先按第 1 节生成结构化报价数据，补充演示规格及交易条款，再渲染成可提取文本的 PDF；报价字段与参考答案分别保存，解析链路只读取上传文件，不能读取生成器答案来填补文件中的缺失信息。
- 为容纳正式 RAG，必交付为 1 种开发版式＋1 种独立留出评测版式，分别覆盖不同表格／措辞；额外开发版式不列为必做。开发集与留出评测集按模板划分，不能只更换随机数；版式与供应商优劣、价格独立变化，缺失字段场景在 PDF 中确实省略该字段。若留出版式被用于调试，须更换未用于开发的最终模板并披露。
- 明确标注合成来源，保留 source_po_id、生成器版本、随机种子和文件版本；原始历史数量不当作 MOQ，历史订单日期不直接当作新报价有效期。合成场景结果与真实报价适应性分开报告。

**首版解析约束：**

- PDF 每份最多 **5 页、5 MB**，单任务最多 **5 份**；作为可配置初值，按样例验证。
- CSV 使用独立的固定字段解析器，每行一份供应商对该商品的报价，进入相同字段契约和业务校验流程。
- 保存文件哈希、解析器版本、页码、文本块 ID 和位置；模型只引用解析器已生成的来源 ID。来源存在不等于支持字段含义，仍需证据校验或人工确认。
- 覆盖全部页面和条款；表格提取失败时保留原文供理解，文本不可用或关键内容无法可靠识别时提示更换文件或人工录入。扫描件首版不增加 OCR 分支，解析失败不伪装成正常空报价。

**6. 数据库和后台任务：已选择 PostgreSQL，采用数据库作业表＋单 worker**

**数据库选型已确定为 PostgreSQL。** 本地开发与 Lightsail 部署使用同一种数据库和一致的迁移脚本。数据访问层采用 **SQLAlchemy＋psycopg**，由 **Alembic** 管理表结构迁移；Pydantic 继续负责接口与结构化数据校验。[SQLAlchemy PostgreSQL 接入](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#module-sqlalchemy.dialects.postgresql.psycopg)

| 部分 | 实现约定 |
| ---- | -------- |
| 核心业务数据 | 采购任务、供应商、报价版本、待补问题、结果、审批和作业使用关系表，设置必要的外键、非空、检查及唯一约束 |
| 原始提取与快照 | 可使用 JSONB 保存提取结果、证据列表和不可变输入快照；经常用于筛选、关联和约束的字段单独建列 |
| 金额 | 数据库使用精确十进制 NUMERIC，Python 使用 Decimal；单价精度按字段契约保留，总额按确认的规则舍入，不能在写入时提前截断单价 |
| 文件 | 原始 PDF、解析文件和报告放在持久化文件存储中；数据库保存文件 ID、哈希、位置和关联版本 |
| 部署 | Docker Compose 增加独立数据库服务和持久化卷，API 与 worker 通过内部网络访问；配置应用账号、健康检查、连接重试和有界连接池 |
| 资源与版本 | 固定经验证的 PostgreSQL 镜像版本；待 Lightsail 内存确认后设置连接池和数据库资源参数 |

PostgreSQL 的 NUMERIC 与 JSONB 分别支持精确数值和结构化 JSON 存储；它们不替代报价语义、证据和业务有效性校验。[数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)、[JSON 类型](https://www.postgresql.org/docs/current/datatype-json.html)

**事务与后台执行约束：**

- 报价更新、影响决策的字段修正及审批采用统一的任务行锁和版本规则。审批在同一短事务内锁定任务、检查权限／当前版本／阻塞问题／有效期，再写入审批记录；过期提交必须拒绝。[PostgreSQL 锁机制](https://www.postgresql.org/docs/current/explicit-locking.html)
- worker 在短事务内领取并标记作业，提交后再解析文件或调用模型。结果写回时核验作业归属和输入版本，旧作业的迟到结果不能覆盖当前结果。
- 作业记录保留输入版本、尝试次数、租约／心跳和执行状态；配合幂等约束与过期作业恢复，防止重复写入和永久停留在执行中。每阶段最多 3 次尝试（含首次），作为可配置初值；重试同时受第 3 节模型调用预算约束，达到限制后记录失败原因并结束当前执行。
- 等待用户补充时保存问题、将任务置为 NEEDS_INPUT，并持久化 LangGraph 中断后结束本次作业；回答通过版本校验后创建恢复作业，按第 3 节恢复对应图运行并重新校验。新报价等其他决策修改创建新图运行。等待模型或用户期间不持有数据库锁。
- 首版保留一个 worker，采用数据库作业表，每个任务最多一个活跃执行，不增加 Redis＋Celery。API 请求和后台执行各自管理数据库会话，不共享活跃事务。
- 数据库用 pg_dump 等受支持方式备份，将备份保存到实例之外并验证恢复；数据库备份需配套文件备份，持久化卷本身不等于备份。[PostgreSQL 备份](https://www.postgresql.org/docs/current/backup-dump.html)

**7. AWS 部署与文件存储：已选择主办方 Lightsail 实例＋Docker Compose**

应用部署到主办方提供的单台 Lightsail 实例，使用 Docker 镜像封装运行依赖，Docker Compose 管理服务、网络、环境配置和持久化卷。首版文件存储使用实例本地持久化卷，不依赖额外对象存储服务。Compose 可使用基础配置与环境覆盖文件组织本地开发和云端部署。[Docker Compose 部署说明](https://docs.docker.com/compose/how-tos/production/)

| 服务／存储 | 实现约定 |
| ---------- | -------- |
| Web 入口 | 提供 React 构建产物，并将 API 请求反向代理到 FastAPI；配置 HTTPS 与必要的访问入口 |
| API | FastAPI 处理请求、权限、版本校验和审批；通过内部网络连接 PostgreSQL |
| worker | 使用与 API 相同版本的后端镜像，以独立启动命令执行 LangGraph 作业；首版运行一个 worker |
| PostgreSQL | 独立数据库容器，使用专用持久化卷，保存业务表及 LangGraph 检查点；不向公网开放数据库端口 |
| 报价与报告文件 | 使用独立的命名卷，按原始报价、解析结果和报告组织目录；API 与 worker 按需挂载同一个文件卷，下载经后端鉴权 |

**版本与环境管理：**

- Git 管理源代码、Dockerfile、Compose 配置、依赖锁定文件和数据库迁移脚本。发布镜像以 Git 提交号或发布版本标记，并记录镜像摘要；云端部署使用构建产物，不依赖临时修改容器内代码。
- 本地开发与 AWS 使用同一套服务定义，通过环境配置切换模型 provider、model_id、接口地址和认证方式，遵循第 4 节。配置模板提交到仓库，真实密钥通过后端运行环境注入。
- 记录每次部署的前后端镜像版本、数据库迁移版本和模型／提示词配置版本；API 与 worker 采用配套版本。数据库迁移由发布步骤统一执行一次，完成后再启动对应应用服务。
- 应用回退采用已验证的旧镜像，并检查它与当前表结构及检查点格式是否兼容；切换镜像不会自动回退数据库、报价版本或审批记录。数据库主版本升级单独规划迁移。
- Lightsail 的内存、CPU、磁盘、系统架构及资源有效期仍需确认，据此设置镜像构建目标、连接池、资源限制、日志轮转和健康检查。

**文件持久化与备份：**

- 持久化卷独立于容器生命周期，容器重建后继续挂载同一卷；正常发布不删除数据卷。数据库卷与文件卷分别保存，文件 ID、哈希、位置及业务版本仍由应用和 PostgreSQL 管理。[Docker 卷说明](https://docs.docker.com/engine/storage/volumes/)
- 文件按不可覆盖的版本路径保存，报价更新生成新文件记录；Docker 镜像版本管理运行程序，报价及审批版本管理业务事实，两者分别记录。
- 按第 6 节执行数据库备份，并配套备份原始文件和报告。备份应保存到实例之外；首版可导出到团队指定的本地备份目录，部署前验证恢复，资源到期前完成导出。
- 部署验证包含容器重建后数据与文件保留、LangGraph 补问恢复、API／worker 健康状态，以及主办方模型接口的完整回归测试。

首版选型已确定：**Electronics／MCU-9＋FastAPI＋Pydantic＋React＋LangGraph＋PostgreSQL＋pdfplumber＋主办方 Lightsail／Docker Compose**，文件使用实例本地持久化卷，模型按本地开发 API→主办方 API 分阶段验证。下一步冻结演示规格表、报价数据模板及接口契约，建立数据库／检查点迁移和容器部署流程，并验证“补问暂停→重启→回答恢复→报价更新”的完整链路。向主办方集中核验：**LangGraph 的比赛适用要求、模型 API 与凭据配置、Lightsail 实例规格及访问方式、额度与资源有效期**。部署平台已确定，具体接入和资源参数仍待确认。
