## 1. 本周目标与当前基线

**本周目标：把已经跑通的后端交付成可以在浏览器上完成“上传 → 补问 → 成本与可行性比较 → 采购合规与供应商资质核验 → 最终推荐 → 审批 → 报价更新 → 重新审批 → 导出报告”的应用。**

Week1 已有本地真实模型、两次持久化中断恢复以及容器重建后数据保留的验收记录；React、正式身份权限、审批、制度 RAG 与供应商合规门禁、同一报价的新版本替换和自动作业执行仍需实现。

## 2. 范围与技术约束

### 2.1 本周必交付

- Electronics／MCU 单商品比较，React 操作界面与来源展示。
- 结构化补问、人工纠正、需求与报价版本更新、人工排除与重新纳入。
- 具名账户、采购用户与审核人权限、版本绑定的人工审批。
- 正式采购合规链路：BM25 稀疏召回、pgvector 稠密召回及 embedding／rerank API 检索适用制度，PostgreSQL 精确查询批准供应商和 RoHS，确定性规则生成合规状态并保留引用。
- 实验性 OCR 辅助提取：扫描 PDF 可进入 OCR，但 OCR 来源的关键字段必须在现有人工审核中确认或纠正后才能进入 C；该路径不作为 MCU-DEMO-001 主演示成功的前提。
- HTML 草稿与最终报告，旧结果／审批失效检查。
- PostgreSQL 作业表驱动的单 worker 调度、受控恢复和幂等保护。
- Lightsail／Docker Compose 部署及主办方模型验证。

### 2.2 本周不增加的范围

开放式聊天、ISO、框架合同、OCR 无人值守自动放行、复杂采购品类、自动下单、多 worker 扩容和报告美化不进入本周范围。Week2 使用现有 PostgreSQL 的 pgvector 扩展和外部 embedding／rerank API；不再引入 Qdrant、FAISS 等第二套向量存储，也不在 Lightsail 部署本地 embedding／rerank 模型。检索组件不得成为报价提取、确定性比较或系统启动的强依赖。

技术栈继续使用 FastAPI＋Pydantic＋React、LangGraph、PostgreSQL 16／pgvector＋SQLAlchemy／psycopg＋Alembic、pdfplumber 和 Docker Compose。RAG 的 embedding／rerank 服务商、模型 ID、向量维度、超时和预算须通过 smoke test 后冻结；向量列维度一经迁移确定，不允许同表混用其他维度。复用 A 的数据契约、B 的解析／审核接口和 C 的 Decimal 规则，不复制领域逻辑。

RAG 是正式必交付模块，不能因时间不足改称拓展项。检索故障可以明确降级为 `REVIEW_REQUIRED`，但不能在缺少依据时默认供应商合规，也不能用降级结果代替正式 RAG 验收。

### 4.1 冻结集成基线和 Week2 接口

**时间：9/14。负责人：A＋D 与 B＋C 共同冻结；D 维护最终接口样例。**

- [ ] 确认并集成最新提取审核修复，运行正常测试及 PostgreSQL 集成测试。
- [ ] 对 V2／V3 证据问题、V5／V6 关键静默错误执行定向真实模型回归。
- [ ] 冻结需求更新、同一报价新增版本、人工排除、审批、报告，以及 RAG 检索与合规状态的请求／响应示例。
- [ ] 区分任务状态、报价审核状态、比较状态和审批状态，前端直接映射共同契约。
- [ ] 明确共享迁移与接口变更的集成顺序，避免多人同时修改同一版本链。

**验收：**A 可依据共同接口开发；测试结果记录到具体代码版本；失败项明确列出，不把“转人工审核”统计为自动提取正确。

### 4.2 从运费专用流程扩展到有限的结构化审核

**时间：9/14–9/16。负责人：前端与业务闭环组 A＋D；B 复核既有审核契约兼容性。**

- [ ] 保留已经验收的两步运费流程。
- [ ] 支持数量／计价基础、供应商名称、交期起算点等阻塞字段的展示与人工处理。
- [ ] 支持多份报价、多个问题，逐项解决后重新调用 B 的审核接口。
- [ ] 将可人工处理的问题转入明确的待审核状态，替代目前部分非运费问题直接使图失败的路径。
- [ ] 对解析失败和模型故障保留独立错误路径，不能伪装成业务字段缺失。

**验收：**只有 `downstream_ready=true` 的对象进入 C；旧问题回答被拒绝；幂等重放不重复推进 revision；用户可以纠正或明确排除报价后继续流程。固定问题和类型化回答为本周边界，不实现开放式对话。

#### 4.2.1 接入实验性 OCR 字段确认

**时间：9/15–9/17。负责人：A＋D 完成审核界面、问题编排和文件访问；B＋C 提供 OCR／证据契约并复核下游门禁。**

- [ ] 扫描页和混合页在显式开启实验开关时执行 OCR，保存 OCR 引擎／语言包／预处理版本、页码、来源 ID、原文、置信度及文件哈希。
- [ ] OCR 来源的关键字段统一创建 `OCR_FIELD_CONFIRMATION` 审核项；复用现有 `ReviewEvent`／`CorrectionEvent` 和 `ReviewEnvelope`，不建立第二套人工审查系统。
- [ ] 后端为每个关键字段建立一个 issue，绑定当前字段候选 artifact、内容哈希和 task revision；React 按报价集中展示这些 issue。每个回答独立留痕，只有当前版本的全部阻塞项解决后才创建 RESUME 作业。
- [ ] 一个审核页面集中展示字段名、提取值、原始文件名、`document_id`、文件版本、页码、`source_id`、OCR 原文和置信度。
- [ ] 页面不嵌入截图或裁剪图片，只提供经过后端授权的“打开原 PDF”链接；不得向浏览器暴露服务器磁盘路径。
- [ ] 用户操作限定为“确认正确”“修改字段”“原文无法辨认”。确认生成 ReviewEvent，修改生成 CorrectionEvent，无法辨认则保持 `REVIEW_REQUIRED`。
- [ ] 人工提交后由系统自动重新运行字段、证据和跨字段审核，不要求用户重复完成第二轮相同字段审查。
- [ ] 非关键 OCR 字段可以按既有 criticality 策略给出警告；关键字段未确认时必须保持 `downstream_ready=false`，高 OCR 置信度不能替代人工确认。
- [ ] OCR 输出作为不可变 artifact 保存；worker 恢复时复用已完成 artifact，不重复执行 OCR。报价文件版本变化后，旧 OCR issue 和确认事件立即失效。

**验收：**用户可以根据系统提供的 PDF 文件、版本和页码在原文件中完成核对；确认／纠正均有版本化审计记录；纠正后自动复核并进入 C；未确认、无法辨认、隐藏文本冲突或来源失效时不得进入下游。当前报价最多 5 页，因此 Week2 不以嵌入图片作为必需能力。MCU-DEMO-001 继续使用原生文本 PDF；OCR 作为独立实验能力验收。

### 4.3 完成制度检索与结构化供应商合规门禁

**时间：9/14–9/17。负责人：RAG 与合规组 B＋C；D 按冻结契约完成迁移和主图集成，A 使用固定响应开发展示。**

- [ ] B 提供 3–5 份虚构英文采购制度，C 提供一个包含 A／B／C 的版本化批准供应商注册表和 RoHS 记录；ISO 与框架合同不进入 Week2 数据集。
- [ ] 制度条款绑定经团队审阅的 `control_code` 和适用参数；先由结构化制度清单按金额／品类／地区／时间确定必需 control_code，再调用 RAG 定位原文。LLM／RAG 不动态创造规则。
- [ ] B 按 policy_set_version、范围和有效期过滤制度，提供统一检索接口；BM25 Top-3 是必须可运行、可离线复现的稀疏检索基线。
- [ ] embedding API 生成条款和查询向量，pgvector 对 SQL 预过滤后的候选执行精确余弦 Top-10；与 BM25 结果融合后，由 rerank API 重排取 Top-3。所有路径通过同一结果契约返回文档／版本／条款 ID、章节、原文、哈希和分数。
- [ ] 向量记录 provider、模型 ID、维度、预处理版本和内容哈希；pgvector 数据绑定制度集合及索引版本，并可从 PostgreSQL 中的权威条款完整重建。首版不建立 HNSW／IVFFlat，只有实测延迟不满足要求时才评估近似索引。
- [ ] B／C 在合规门禁前核验所有必需 control_code 均有受支持的条款命中；漏召回、引用不支持或版本不一致统一进入 REVIEW_REQUIRED，不能减少检查项后判为合规。
- [ ] C 定义 supplier master、身份映射、registry version、批准记录、RoHS、检索轨迹、合规 assessment 和 review event 的字段与约束，D 统一生成迁移。上传时的 supplier_id 仅为声明值，匹配不明确必须补问。
- [ ] C 对所有 `FEASIBLE` 候选执行 SQL 精确查询和确定性规则，生成 `COMPLIANT`、`REVIEW_REQUIRED` 或 `NON_COMPLIANT`；相似度分数不能直接决定合规。
- [ ] 一次生成全部可行候选的合规矩阵：高排名候选为 REVIEW_REQUIRED 时阻止最终推荐；明确 NON_COMPLIANT 后才可选择下一名 COMPLIANT 候选。
- [ ] 合规结果绑定 `task_revision + policy_set_version + supplier_registry_version + retrieval_id`；推荐、审批和报告冻结引用。显式切换版本才推进 revision 并使旧结果／审批失效。
- [ ] 人工补证创建新供应商记录版本；人工确认使用 `ComplianceReviewEvent`，与最终审批分离。Week2 不实现无证据的任意合规豁免。
- [ ] 每文档提取预算保持 8 次；制度导入 embedding、查询 embedding、rerank 和解释分别持久化次数、延迟及用量，恢复不得重置。

**验收：**初步价格第一的供应商必须通过适用制度、可信供应商身份、批准状态和有效 RoHS 核验后才能成为最终推荐；命中证据可以回到原文／原记录。`NO_EVIDENCE`、`CONFLICT`、`ERROR` 均转为 `REVIEW_REQUIRED` 并分别展示。BM25、pgvector 和 rerank 三段须分别报告 Recall、延迟与失败降级结果，并保留融合前后的候选轨迹。RAG 不补报价事实、不改金额、价格排序或合规状态；确定性门禁决定是否有足够依据发布推荐。

运行索引只读取明确允许的制度集合。报价参考答案、评测标签、生成器映射和项目说明不进入索引或模型提示词。英文制度与英文查询为首版边界。批准供应商和 RoHS 通过版本化关系表查询，不进入向量召回来决定事实真伪。

#### 4.3.1 最小持久化与接口契约

| 分组 | Week2 最小对象 |
| --- | --- |
| 制度 | `policy_sets`、`policy_documents`、`policy_clauses`、`policy_clause_embeddings vector(dim)`、`retrieval_traces`；保存 embedding 配置、内容哈希和检索版本 |
| 供应商 | `supplier_masters`、`supplier_registry_versions`、`supplier_approval_records`、`supplier_rohs_records` |
| 运行 | `supplier_identity_matches`、`compliance_assessments`、`compliance_review_events` |
| 审批／报告 | `approvals`、`reports`，均绑定当前 result、snapshot 和 task revision |

制度与供应商数据通过白名单 manifest 和内部 CLI 幂等导入，不开放“索引任意服务器路径”的公共 API。任务创建时绑定两个已经发布的集合版本；结果接口返回初步排序、逐供应商合规矩阵和最终推荐三部分。

公开接口最少增加：

- `GET /api/v1/tasks/{task_id}/compliance`：读取当前及历史合规矩阵和来源；
- 扩展现有 issue answer 联合类型，支持 `SUPPLIER_MATCH`、受控的 `COMPLIANCE_EVIDENCE_CONFIRMATION` 和 `OCR_FIELD_CONFIRMATION`；

预算初值为：每个检索步骤的 query embedding、rerank、解释分别最多 2 次尝试（含首次），制度导入 embedding 单独按批次记账。BM25 和 pgvector 数据库查询不消耗模型调用预算。参数可配置，但同一 graph run 恢复时不得重置。
