# DATA

**这个比前面提到的发票数据集更贴近你们的业务，值得采用。** 我的建议是：把它作为**包装盒演示数据的基础素材**，补充报价条款后用于比选；原始数据本身还不能直接完成整条流程。

我已读取仓库实际的 [purchase_orders.csv](https://github.com/dytcoke23/procurement-spend-analysis-dashboard/blob/main/data/purchase_orders.csv)，结果如下：

| 项目                        | 实际情况                       |
| --------------------------- | ------------------------------ |
| 采购记录                    | 47,128 条                      |
| 供应商                      | 106 家                         |
| 商品类别                    | 10 类                          |
| Packaging 包装类记录        | 5,706 条                       |
| Corrugated Boxes 包装盒记录 | **1,130 条，覆盖 11 家供应商** |

**1. 它的优势：你们需要的商品和供应商基础已经存在**

数据包含供应商、商品、单价、采购数量、付款条件、订单日期、承诺交付日期和实际交付日期。因此，可以从包装盒记录中选取供应商和价格样本，不必从零设计全部业务数据。

仓库明确说明这些是**固定随机种子生成的合成数据**，项目声明采用 MIT 许可证。它能提供可复现的演示素材，但不能作为真实企业业务验证的证据。[项目说明](https://github.com/dytcoke23/procurement-spend-analysis-dashboard)、[许可证](https://github.com/dytcoke23/procurement-spend-analysis-dashboard/blob/main/LICENSE)

**2. 它缺少的内容，会直接影响你们的比选逻辑**

| 数据情况                         | 对你们的影响                                   |
| -------------------------------- | ---------------------------------------------- |
| 有历史采购单价                   | 可以作为样例价格基础，不能视为当前有效报价     |
| 有历史采购数量                   | **不能把采购数量当作 MOQ**                     |
| 商品写着 `per 1000`              | 表示计价口径，不能直接认定每箱装 1,000 个      |
| 有承诺／实际交付日期             | 可以分析历史交付表现，不能直接视为本次报价承诺 |
| 没有币种字段                     | **不能看到 `$` 就默认是 SGD**                  |
| 没有尺寸、材质等详细规格         | 商品名称相同仍不足以证明严格可比               |
| 没有 MOQ、运费、税费和报价有效期 | 需要作为新增合成字段明确补充                   |
| 没有原始供应商报价 PDF           | 需要生成文档，才能验证 pdfplumber＋LLM         |

这些判断来自实际 CSV 字段及其 [数据生成代码](https://github.com/dytcoke23/procurement-spend-analysis-dashboard/blob/main/scripts/generate_data.py)。

例如，一条包装盒记录的单价为 `666.98`、数量为 `11`、总额为 `7336.78`。结合商品名 `Corrugated Boxes (per 1000)`，应按 **11 个“千个计价单位”**理解，即 11,000 个盒子；这条记录并没有说明包装箱数或最低采购量。

**3. 我建议这样用于你们的项目**

保留原始数据，再单独生成你们自己的报价测试集：

```
原始包装盒采购记录
→ 选取 3–5 家供应商作为场景素材
→ 明确商品规格、币种及计价单位
→ 补充 MOQ、包装、运费、交期和有效期
→ 生成不同版式的文本 PDF／CSV
→ 人工核验成本、可行性和预期推荐
```

新增字段应标记为团队设计的合成条件，并保留原始 `po_id` 作为素材来源。**生成的报价不能表述为这些供应商历史上真实提交过的报价。**

可以围绕它组织三组场景：

- **正常比较：**不同供应商、包装单位、MOQ 和运费，计算实际总成本。
- **缺失与冲突：**删除运费、制造交期歧义，验证补问。
- **报价更新：**修改某家交期或价格，验证重算和旧审批失效。

若沿用原来的“S$300 买 1,000 个盒子”案例，需要重新校准价格或预算，避免把两套不同价格设定直接混用。

**4. 原项目的供应商风险评分，建议暂时不搬过来**

原仓库人为设置了部分高延迟、高拒收率供应商，并使用加权规则和异常检测生成风险评分。这适合展示该数据的预设规律，不能证明真实供应商风险。[生成逻辑](https://github.com/dytcoke23/procurement-spend-analysis-dashboard/blob/main/scripts/generate_data.py)

你们可以后续增加“历史准时交付率”作为辅助信息，但首版仍以当前报价的硬约束和用户偏好排序。如果加入历史表现，只使用决策时点之前已知的记录，避免利用未来交付结果。

**因此，我会把这个数据集提升为你们的首选业务素材来源。** CompanyDocuments 可保留用于额外的提取测试；核心包装盒场景则基于这个数据集补齐条款、生成报价文档，更容易形成一致且可验证的演示。



需要补的主要是 **“本次报价条款”和“采购需求”**。原数据已经有供应商、商品名称、历史单价、采购数量、付款条件和交付日期，但它记录的是历史订单，不能直接作为当前报价。[原始字段定义](https://github.com/dytcoke23/procurement-spend-analysis-dashboard/blob/main/scripts/generate_data.py)

建议保留原 CSV，另外建立报价场景数据。下面是针对你们 MVP 的字段清单。

**1. 每份供应商报价需要新增或明确的字段**

| 字段组         | 建议字段                                     | 为什么需要                                                   | 补全方式                                   |
| -------------- | -------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------ |
| 报价身份       | `quote_id`、`quote_version`、`scenario_id`   | 将多家报价归入同一个采购任务，并支持更新                     | 系统生成                                   |
| 商品规格       | `product_spec`                               | 原来的“Corrugated Boxes”没有尺寸、材质等信息，无法确认商品等价 | 团队定义固定规格，并写入模拟报价           |
| 基本计数单位   | `base_unit`                                  | 明确数量最终统一为“个”                                       | 包装盒场景设为 `piece`                     |
| 计价口径       | `price_basis_quantity`、`price_basis_unit`   | 明确单价对应每个、每箱还是每千个                             | 从原商品名提取候选口径，再核验             |
| 包装与采购步长 | `units_per_pack`、`order_multiple_units`     | 决定是否必须整箱采购，以及如何向上取整                       | 新增模拟条款                               |
| 起订量         | `moq_quantity`、`moq_unit`                   | 原采购数量不是 MOQ                                           | 新增模拟条款，明确单位                     |
| 币种           | `currency`                                   | 原数据没有币种字段                                           | 模拟报价明确设为 SGD，并说明属于新场景设定 |
| 运费           | `shipping_fee_status`、`shipping_fee_amount` | 计算总成本，区分未知、免费和已包含                           | 新增模拟条款                               |
| 税费口径       | `tax_mode`，必要时附税额或适用规则           | 确保报价总额与预算使用相同口径                               | 首版采用明确一致的简化口径                 |
| 其他费用       | `other_fees`、`fees_complete`                | 避免漏掉已声明的处理费等费用                                 | 明确列出，或在模拟报价中声明无其他费用     |
| 当前交期       | `delivery_date`，或明确的交期字段组          | 历史交付日期不能代表新报价承诺                               | 新增当前场景的交付条款                     |
| 报价时间       | `quote_date`、`valid_until`                  | 检查报价是否有效，演示自然过期                               | 新增模拟日期                               |

有几个容易混淆的地方：

- **`per 1000` 只是计价口径，不证明每箱装 1,000 个。**
- 包装数量和采购步长也不同：每箱 100 个，可能允许拆箱，也可能必须整箱购买。
- 运费为 `UNKNOWN` 时金额应为空；明确免费才能按零计算。
- 新场景设为 SGD，不代表原数据的金额已经被确认是 SGD，也不是完成了汇率换算。

交期可以选择两种表达方式，首版不必两种都强制填写：

| 方式             | 必要字段                                                     | 实现建议                                   |
| ---------------- | ------------------------------------------------------------ | ------------------------------------------ |
| **明确到货日期** | `delivery_date`                                              | 最简单，建议作为标准化结果                 |
| 相对交期         | `lead_time_days`、自然日／工作日、发货／到货、起算事件、起算日期 | 用于文档理解和补问；信息齐全后换算到货日期 |

**2. 原数据已有字段：可以复用，但需要保留历史含义**

| 原字段                         | 可以怎么用                          | 不能直接怎么用                   |
| ------------------------------ | ----------------------------------- | -------------------------------- |
| `supplier_id`、`supplier_name` | 作为模拟供应商身份                  | 不能称为真实企业验证数据         |
| `category`、`item`             | 筛选包装盒记录，建立商品素材        | 名称相同不等于详细规格一致       |
| `unit_price`                   | 作为新模拟报价价格的参考            | 不能称为供应商当前有效报价       |
| `quantity`                     | 参考历史订单规模                    | 不能当作 MOQ 或本次需求量        |
| `payment_terms`                | 作为模拟付款条款素材                | 不能默认历史条款仍适用本次采购   |
| `line_total`                   | 校验原始记录的金额关系              | 不能当作本次含运费、税费的总成本 |
| `po_id`                        | 保存为 `source_po_id`，追踪素材来源 | 不能直接充当新报价编号           |

**不要为了填满字段而让 LLM 猜测这些商业条件。** 对演示数据，由团队明确设计；未来处理真实报价时，则从原文提取或向用户补问。

**3. 采购需求需要单独补充，不属于供应商报价**

同一场景下，各家供应商应该面对同一份需求：

| 需求字段                                    | 示例／作用                               |
| ------------------------------------------- | ---------------------------------------- |
| `required_product_spec`                     | 要求的包装盒尺寸、材质、是否印刷等       |
| `required_quantity`、`quantity_unit`        | 1,000 个                                 |
| `budget_amount`、`currency`、`budget_basis` | 预算金额、SGD、预算是否包含运费和税费    |
| `delivery_deadline`                         | 最迟到货日期                             |
| `delivery_location`                         | 固定收货地点，避免比较不同配送条件的运费 |
| `planned_order_date`／已确认起算日期        | 用于换算相对交期                         |
| `ranking_preference`                        | 成本优先或到货优先                       |
| `secondary_preference`                      | 可选；未指定时允许并列                   |
| `requirement_version`                       | 修改数量、预算或交期后产生新版本         |

例如，**需求量 1,000 个、MOQ 2,000 个、实际需要采购 2,000 个**，这三个数量应分别保存。实际采购量由程序计算，不是另一个随意补填的输入。

**4. 来源、版本和测试答案也需要新增**

这些字段用于证明系统正确处理了数据，而不是商业报价本身。

| 类型         | 建议保存的内容                                       |
| ------------ | ---------------------------------------------------- |
| 数据来源     | 原仓库、数据版本或文件哈希、`source_po_id`           |
| 新增字段来源 | 团队模拟设定、原始字段映射、人工修正或程序计算       |
| 文档来源     | `document_id`、文件版本、页码／文本块、原文片段      |
| 字段状态     | 已提取、已核验、缺失、冲突                           |
| 变更记录     | 操作者、时间、修改前后值                             |
| 测试参考答案 | 预期采购量、总成本、可行性、阻塞问题、推荐／并列结果 |

**测试参考答案要与 Agent 输入分开。** 它们用于评测，不能作为工具读取的业务数据，否则模型可能直接看到正确推荐。

此外，为了测试补问，有些输入应当**故意不完整**：例如参考答案知道 B 运费为 S$20，但初始报价 PDF 不提供该金额，只有模拟用户回答后才进入业务状态。

历史交付表现属于可选扩展：可以从订单日期与交付日期计算历史承诺周期、实际周期和延迟情况，但不能用它们自动补成本次报价交期；历史分析也只能使用决策时点之前已知的数据。

建议先补齐 **规格、计价单位、包装步长、MOQ、币种、费用、当前交期和有效期**，然后生成报价 PDF、采购需求和独立参考答案。这些就足以支撑你们第一版的完整比选闭环。
