# QQFARM 采购偏好与供应商信息页实施方案（V2）

> 文档状态：已实施  
> 更新日期：2026-09-21  
> 本版依据：原《偏好更新方案》、当前 lc 分支实现和评审意见  
> 核心决策：六个指标均可选择；每次决策使用一个主指标和至多一个次指标；其余指标只计算和展示，不参与本次排序。

## 1. 文档目的

本文档给出采购比较偏好、供应商历史表现和“供应商信息”页面的统一实施方案，使系统覆盖以下四类比较维度：

1. 价格。
2. 交货周期。
3. 付款条件。
4. 供应商历史表现。

本次改造以比赛演示可完成、结果可解释、输入可冻结、历史可追溯为优先目标。

系统仍坚持以下边界：

- 确定性代码负责金额、日期、状态、排序、评级和版本。
- 大模型负责理解自然语言、解释冻结结果和提出待确认的偏好变更。
- 大模型不能创造数据、隐藏使用权重、改变硬性可行性或自行选择赢家。
- 历史表现不等同于供应商合规、资质、信用或采购批准。
- 本次不建设完整的供应商主数据管理后台。

## 2. 本版确认的产品规则

### 2.1 六个原子排序指标

系统提供六个可选的原子排序指标：

| 核心维度 | 枚举值 | 中文名称 | 排序方向 |
|---|---|---|---|
| 价格 | LOWEST_CONFIRMED_TOTAL_COST | 最低已确认总成本 | 越低越优 |
| 交货周期 | FASTEST_CONFIRMED_DELIVERY | 最快已确认到货 | 越早越优 |
| 付款条件 | LONGEST_CONFIRMED_PAYMENT_TERM | 最长已确认账期 | 越长越优 |
| 供应商表现 | HIGHEST_SUPPLIER_PERFORMANCE | 综合历史等级最高 | A 优于 B、C、D |
| 供应商表现 | HIGHEST_HISTORICAL_ON_TIME_RATE | 历史准时率最高 | 越高越优 |
| 供应商表现 | LOWEST_HISTORICAL_REJECTED_LINE_RATE | 历史拒收订单行率最低 | 越低越优 |

### 2.2 每次只允许主、次两个指标影响排序

- 主指标必选。
- 次指标可选。
- 主指标和次指标不能相同。
- 不支持第三顺位、自由权重或大模型隐式加权。
- 次指标只在主指标最佳组存在并列时触发。
- 成本容差形成的候选组也视为主指标并列组。
- 未选中的其余指标仍在供应商信息页和比较矩阵中展示，但绝不改变本次排名。
- 如果主、次指标都无法打破并列，系统必须返回并列，不得用报价 ID、上传时间或供应商名称暗中选出赢家。
- 六项是平台级能力；三项历史指标只有在当前任务存在 scope 匹配且可用的历史数据绑定时才允许选择。
- OUT_OF_SCOPE 时前端禁用历史指标，后端返回 422 和 ranking_criterion_not_applicable；不能让任务进入永远无法解除的 PENDING_INPUT。

这意味着“四个维度全部进入系统”是指四类数据均可被计算、核查和选择，不代表每次排序同时使用全部四类维度。

## 3. 实施前基线与实际缺口（历史记录）

实施前系统已经具备：

- 报价价格提取、确定性成本计算和预算校验。
- 交货信息提取、预计到货日期计算和截止日期校验。
- payment_terms 字段提取，以及部分 N30、Net 30 文本规范化。
- ProcurementRequirement 中的 ranking_preference 和 secondary_preference。
- 成本、交期两个指标的主次排序。
- Decision Profile、供应商排除和成本容差。
- Scenario 持久化、baseline/delta、STALE、确认和 Apply。
- 自然语言 Intent、多轮 Conversation、异步 Worker 和流式响应。
- Requirement、Quote、Input Snapshot、Result、Summary 和审计版本。

实施前尚未具备：

- 付款条件经过审核后进入规则引擎并参与排序。
- 供应商历史表现数据集、受控 Loader 和任务版本绑定。
- 历史指标的确定性评级及排序。
- 新旧偏好模型的完整兼容适配。
- 付款和历史事实的 LLM grounded validation。
- 当前任务范围内独立的供应商信息页面。

本次并非从零开始推翻排序模型。准确的改造描述为：

> 扩充现有原子排序指标，并将 Decision Profile、Scenario、Intent 和 Conversation 中的组合 ranking_mode 迁移为主、次原子字段。

### 3.1 最新 main 工作流衔接要求

本方案以 main 提交 267d9fa（feat: refine procurement review and decision workflow）为实施基线。该版本新增报价重新启用、报价修订审核继承、集中审核问题分类、税费比较口径和历史结果重新分析入口。实施时必须保留这些能力，并满足以下五项衔接要求。

#### 3.1.1 审核继承不能绕过新增付款字段

main 已支持修改报价时继承同一原件的已审核字段。继承仅在 Review Schema、Review Policy 和字段字典版本均匹配时有效。

本次新增 DECISION_CONDITIONAL、payment_start_event 或付款证据要求时必须：

- 提升 REVIEW_POLICY_VERSION。
- 字段合同发生变化时同步提升 Review Schema 或 Dictionary 版本。
- 旧审核产物不得直接视为付款条件已经满足新规则。
- 审核继承继续保留，但版本不匹配时必须重新生成审核产物。
- 测试证明旧付款审核不会绕过新字段或新起算口径。

#### 3.1.2 付款额外信息使用专门的回答路径

main 已区分：

- FIELD_CORRECTION：原报价事实错误，可修正字段。
- ADDITIONAL_INFORMATION_REQUIRED：原报价事实有效，但缺少换算或评估信息。
- REEXTRACT_OR_SYSTEM_REPAIR：需要重新解析或系统修复。

PAYMENT_BASIS_MISMATCH、缺少 payment_start_event 和复杂付款补充说明不得通过改写原 payment_terms 解决，应进入 ADDITIONAL_INFORMATION_REQUIRED。

实施必须增加可提交的 Issue answer schema 和前端控件，至少支持：

- payment_start_event。
- 补充说明。
- 来源类型和证据引用。
- expected task revision。

回答后推进 revision、写入审计、继续同一个 Graph 并重新计算。不能只显示“需要补充信息”却不给用户解除阻塞的入口。

#### 3.1.3 停用与重新启用报价纳入版本规则

main 新增 POST /api/v1/tasks/{task_id}/quotes/{quote_id}/reactivate。停用或重新启用均属于权威输入变化。

因此：

- QUOTE_DEACTIVATED 和 QUOTE_REACTIVATED 都默认复制上一 revision 的历史数据 binding，不自动升级数据集。
- 两者都使当前 Result、Scenario、Intent、Conversation 和 Summary 失效，并 supersede 活动作业。
- SupplierInfo CURRENT 模式只统计当前 active 报价。
- HISTORICAL_RESULT 继续显示当时冻结的 in_scope_at_result，不受今天 active 状态影响。
- 审计记录必须同时展示报价状态变化和未变化的历史数据版本。

#### 3.1.4 演示报价必须具有一致税费比较口径

main 已支持 EXCLUDED、INCLUDED 和 NOT_APPLICABLE，但含税与不含税报价跨口径比较时，如果没有确认税率或税额，会产生 TAX_CONVERSION_REQUIRED。

preference_demo 的四份报价必须与 Requirement 使用相同、明确的税费口径；第一版建议统一使用 EXCLUDED。否则报价会在偏好排序前进入 PENDING_INPUT，破坏“全部满足硬性要求”的演示前提。

SupplierInfo 的成本图只读取规则引擎确认的 total_cost。前端不能使用 unit_price 自行跨税费口径换算。

#### 3.1.5 偏好选择器复用最新折叠表单

main 的 RequirementFields 同时支持普通模式和 deferAdvancedFields 模式；次偏好在新建任务页的“更多设置”中。

实施六个指标时必须提取共享的 RankingCriterionSelect 和分组选项源：

- 普通模式和折叠模式使用同一组选项。
- 主次互斥、历史 scope 适用性和禁用原因由同一函数计算。
- 后端继续执行相同验证。
- 不允许其中一个入口仍只显示旧的成本/交期两项。
- 是否折叠次偏好只影响界面布局，不改变 API 或 Effective Preferences。

## 4. 范围决策

### 4.1 本次必须实现

- 六个原子排序指标。
- 每次一个主指标、至多一个次指标，其余指标仅展示。
- 标准 Net N 付款条件的确定性比较。
- 基于 MCU-9 历史记录生成版本化供应商表现数据。
- 综合等级、准时率、拒收订单行率三个历史排序指标。
- 可信的供应商身份匹配状态。
- 数据集适用范围、as-of、版本和内容哈希冻结。
- 硬性可行性与排序可比较性分离。
- 权威 ranking trace。
- 旧任务、旧 Scenario 和旧结果继续可读。
- 任务内“供应商信息”独立页面。
- Summary 和聊天只能解释冻结事实。

### 4.2 本次不实现

- 全局供应商主数据 CRUD。
- 联系人、地址、网站、企业注册、真实证书或制裁数据。
- 真实财务风险、产能、信用评分和跨任务中标率。
- 用户上传任意历史数据并自行配置评级公式。
- 现金折扣、信用证、分期付款和预付款比例的自动优劣判断。
- 动态加权总分或雷达图式综合分。
- 使用 RAG 或大模型计算供应商评级。
- 自动淘汰无历史数据的新供应商。
- 将拒收订单行率描述成产品缺陷率或数量不良率。

## 5. 核心业务语义

### 5.1 硬性要求与排序偏好分离

以下内容继续属于硬性采购要求：

- 型号、制造商、封装、版本和成色。
- 数量、单位、MOQ 和包装约束。
- 预算上限。
- 最晚交付日期。
- 替代料规则。
- 必须明确的费用和税费。

供应商历史等级、准时率、拒收订单行率和付款账期不能让一份违反硬性要求的报价重新变为可行。

执行顺序固定为：

1. 报价字段提取与审核。
2. 规格、数量、预算、交期等硬性校验。
3. 应用用户明确的供应商排除。
4. 得到本次在范围内的可行候选集合。
5. 检查主指标可比较性。
6. 形成主指标最佳组。
7. 最佳组存在多个候选时检查并应用次指标。
8. 仍无法区分时返回并列。

### 5.2 硬性状态与指标可比较性分离

报价的硬性状态继续使用：

| 状态 | 含义 |
|---|---|
| FEASIBLE | 已满足当前硬性采购要求 |
| INFEASIBLE | 已确认违反至少一项硬性要求 |
| PENDING | 仍有可能影响硬性可行性的关键事实待确认 |

每个排序指标另外保存独立状态：

| 状态 | 含义 |
|---|---|
| COMPARABLE | 该指标有已审核、可用于确定性比较的值 |
| MISSING | 当前没有该指标值 |
| INCOMPARABLE | 有文本或数据，但按当前规则不能安全比较 |
| NOT_APPLICABLE | 数据集范围或指标不适用于当前报价 |

付款条件或历史数据缺失不能把报价本身改成 INFEASIBLE。

硬性 PENDING 继续遵守现有安全规则：如果该报价仍可能影响选择，不能发布最终推荐。

### 5.3 缺失值阻塞算法

第一版采用保守且可测试的算法：

1. 先应用用户明确的供应商排除。
2. INFEASIBLE 不进入排序，但保留在结果中解释原因。
3. 对未排除的 PENDING 先执行决策影响判断；能被确定性证明不会改变当前结果时仅提示，否则结果进入 PENDING_INPUT。
4. 付款和历史排序第一版没有经过验证的 dominance proof，因此存在 hard PENDING 时保守阻塞。
5. 只对剩余 hard_status 为 FEASIBLE 的候选执行偏好排序。
6. 任一候选的主指标不是 COMPARABLE 时，结果进入 PENDING_INPUT，不发布唯一推荐。
7. 主指标全部可比较后，确定主指标最佳组。
8. 如果最佳组只有一个候选，次指标不触发；其他候选的次指标缺失只作为提示。
9. 如果最佳组有多个候选，才检查次指标。
10. 最佳组内任一候选的次指标不是 COMPARABLE 时，结果进入 PENDING_INPUT。
11. 次指标仍相同则返回并列。
12. 未被选择的指标无论是否缺失，都只展示，不参与推荐。
13. 所有候选均不可行、仍有硬性待确认、以及用户排除后范围为空，必须是三种不同结果。

数据集文件缺失、损坏或哈希不一致属于系统错误，不能伪装成供应商 N 级或 NO_DATA。

### 5.4 确定性计算与解释

- 价格、日期、账期、比例和等级由确定性代码计算。
- 排序过程由后端返回 ranking trace。
- 前端、Summary 和聊天只展示或解释后端 trace，不重新实现排序。
- 大模型输出的数值、等级、样本量、推荐和引用必须通过冻结事实校验。

## 6. 偏好模型与兼容设计

### 6.1 新的有效偏好模型

建议新写入的 Decision Preferences 采用以下字段：

| 字段 | 规则 |
|---|---|
| schema_version | 固定记录偏好载荷版本 |
| primary_criterion | 必填，六个原子指标之一 |
| secondary_criterion | 可空，不得等于主指标 |
| excluded_supplier_ids | 保留现有排除能力 |
| cost_tolerance_amount | 保留现有能力，仅成本为主指标时有效 |

ProcurementRequirement 继续保存任务创建时的初始主、次偏好。

最新 Decision Profile 保存完整的当前有效偏好，而不是语义不清的局部覆盖。每次 Input Snapshot 和 Result 必须冻结 resolved effective preferences。

字段映射固定为：

| 来源 | 主指标字段 | 次指标字段 |
|---|---|---|
| ProcurementRequirement 初始值 | ranking_preference | secondary_preference |
| DecisionProfile V2 | primary_criterion | secondary_criterion |
| RequirementChanges V2 | primary_criterion | secondary_criterion |
| Effective Preferences | primary_criterion | secondary_criterion |

DecisionProfile 不存在时，从 Requirement 初始化 Effective Preferences；存在时由完整 DecisionProfile 覆盖。上述字段全部使用 RankingCriterion 类型，不继续使用无约束字符串。

### 6.2 成本容差语义

- 只有 primary_criterion 为 LOWEST_CONFIRMED_TOTAL_COST 时允许 cost_tolerance_amount。
- 确认总成本不高于最低成本加容差的报价组成主指标最佳组。
- 如果设置了次指标，使用用户选择的次指标在该组中继续排序。
- 如果没有次指标，容差组内保持并列。
- 不再隐式固定使用交期作为容差组内的第二排序项。
- 用户切换成非成本主指标时，必须明确确认清除成本容差。
- 后端不得静默忽略、继承或转换不合法的容差。

### 6.3 旧值兼容

旧 RankingMode 映射如下：

| 旧值 | 新主指标 | 新次指标 |
|---|---|---|
| LOWEST_CONFIRMED_TOTAL_COST | LOWEST_CONFIRMED_TOTAL_COST | 空 |
| FASTEST_CONFIRMED_DELIVERY | FASTEST_CONFIRMED_DELIVERY | 空 |
| LOWEST_COST_THEN_FASTEST_DELIVERY | LOWEST_CONFIRMED_TOTAL_COST | FASTEST_CONFIRMED_DELIVERY |
| FASTEST_DELIVERY_THEN_LOWEST_COST | FASTEST_CONFIRMED_DELIVERY | LOWEST_CONFIRMED_TOTAL_COST |

兼容范围必须覆盖：

- DecisionProfile.payload。
- DecisionScenario.changes 和 simulated。
- DecisionIntent.parsed_changes。
- Conversation 中的 proposed changes。
- Input Snapshot。
- 幂等响应和历史 API 载荷。

采用“双读单写”：

- 读取时同时接受旧 ranking_mode 和新主、次字段。
- 新写入只保存新结构。
- 同一请求同时提供新旧字段且语义冲突时返回 422。
- 已冻结历史 artifact 按自身 schema/rule version 读取，不做原地改写。
- 新增字段对旧结果必须可空，前端显示“当时未记录”。

## 7. 供应商历史数据方案

### 7.1 权威来源与诚实标识

唯一权威源文件为：

- data/source/purchase_orders.csv
- 当前 SHA-256：fba22a467e5dd800a0af960930d2ca5e2ecbd9d2bc747e37304867d8d031ae21

data/source/electronics_purchase_orders.csv 是派生子集，不能与源文件同时读取或重复统计。当前两份文件哈希不同，生成器必须明确记录实际输入。

上游数据由固定随机种子生成，是合成数据。输出和页面必须包含：

- is_synthetic = true。
- 来源项目和许可证归属。
- “合成演示历史”标识。

### 7.2 数据集范围

第一版只发布以下范围：

| 字段 | 值 |
|---|---|
| category | Electronics |
| item | Microcontroller MCU-9 |
| 记录数 | 1,185 |

该数据不能直接应用到其他物料。

任务必须通过受控结构化映射绑定 scope，例如将虚构料号 QW-MCU9-DEMO 映射到上述 product scope。不得由模型或前端根据名称猜测。

不匹配时返回 OUT_OF_SCOPE 和 NOT_APPLICABLE，不得当作 N。

### 7.3 版本化输出

建议新增：

- scripts/generate_supplier_performance.py
- data/generated/supplier_history/mcu9/{dataset_version}/supplier_performance.json
- data/generated/supplier_history/mcu9/{dataset_version}/manifest.json

数据集元数据至少包括：

| 字段 | 含义 |
|---|---|
| schema_version | JSON 契约版本 |
| dataset_id | 稳定数据集 ID |
| dataset_version | 不可覆盖的发布版本 |
| content_sha256 | canonical supplier_performance.json 字节的 SHA-256，由不可变 manifest 保存 |
| manifest_sha256 | canonical manifest 的 SHA-256，任务绑定同时保存 |
| rating_method_version | 评级算法版本 |
| scope | category、item 和允许的任务映射 |
| as_of_date | 决策时允许使用的数据截止日 |
| period_start / period_end | 实际统计区间 |
| lookback | 全期间或固定窗口 |
| min_sample_size | 第一版为 10 |
| thresholds | A/B/C/D 阈值 |
| source_path / source_sha256 | 权威源文件信息 |
| generator_version | 生成器版本 |
| is_synthetic | 固定为 true |

generated_at 必须作为显式、可复现的生成参数。manifest 和数据文件均不可覆盖；任务同时绑定 content_sha256 与 manifest_sha256，不能留下未被哈希保护的可变来源元数据。

数组顺序、字段顺序、UTF-8 编码和结尾换行必须固定，以支持 canonical output 测试。

### 7.4 指标定义

准时订单行定义为：

    actual_delivery_date <= promised_delivery_date

第一版清洗和窗口规则固定为：

- category 和 item 使用去除首尾空格后的精确匹配。
- 日期必须是合法 ISO 日期；缺失或非法的 promised_delivery_date、actual_delivery_date 使生成失败，不静默跳过。
- 只纳入 order_date 不晚于 as_of_date，且 actual_delivery_date 不晚于 as_of_date 的已完成记录。
- lookback 以 order_date 判断；period_start 和 period_end 也基于实际纳入记录的 order_date。
- 重复 po_id 使生成失败，不进行隐式去重。
- quality_rejected 去除首尾空格后只接受 True 或 False；其他编码使生成失败。
- 生成失败必须报告行号和原因，不得保留部分结果冒充完整数据集。

聚合指标为：

    on_time_rate = on_time_order_line_count / valid_delivery_order_line_count
    rejected_line_rate = rejected_order_line_count / valid_quality_order_line_count

排序和等级判断使用整数分子、分母或高精度 Decimal。四位小数仅用于显示，不能用显示值制造并列或跨越等级边界。

### 7.5 综合等级

第一版采用版本化的演示评级规则：

| 等级 | 同时满足的条件 |
|---|---|
| N | 存在历史记录，但 delivery/quality 任一有效分母少于 10 |
| A | 两个分母均充足，准时率至少 90%，拒收订单行率至多 2% |
| B | 两个分母均充足，准时率至少 80%，拒收订单行率至多 5% |
| C | 两个分母均充足，准时率至少 70%，拒收订单行率至多 10% |
| D | 两个分母均充足但未达到 C |

判断顺序必须先检查 N，再按 A、B、C、D 判断。否则少量完美记录可能被错误评为 A。

完全没有历史记录时 overall_grade 为空，并使用 history_availability_status=NO_DATA；不能用 N 隐藏“无记录”和“有记录但样本不足”的差别。

N 不是 D，也不表示负面评级。样本不足时：

- 综合等级不可用于自动排序。
- 准时率以 valid_delivery_order_line_count 单独判断是否达到 min_sample_size。
- 拒收订单行率以 valid_quality_order_line_count 单独判断是否达到 min_sample_size。
- 综合等级只有两个分母都达到 min_sample_size 才可比较。
- 页面仍可显示原始分子、分母和“低样本”说明。

这套阈值是比赛演示评分规则，不宣称为行业标准或 SME 认可规则。

### 7.7 供应商身份绑定

上传报价中的 supplier_id 是声明值，不是经过认证的供应商身份。

历史绑定至少需要：

身份匹配和历史可用性是两个独立维度：

| identity_match_status | 处理 |
|---|---|
| MATCHED | ID 存在，且报价显示名称与版本化目录或别名表一致 |
| REVIEW_REQUIRED | 名称缺失、别名未登记或证据不足，暂不使用历史指标 |
| CONFLICT | ID 与名称冲突，阻止历史排序 |

| history_availability_status | 处理 |
|---|---|
| AVAILABLE | 有适用且样本充足的数据 |
| INSUFFICIENT_SAMPLE | 有记录但对应指标样本不足 |
| NO_DATA | 身份已确认，但数据集中没有记录 |
| OUT_OF_SCOPE | 当前任务不在数据集适用范围 |

dataset_status 只使用 AVAILABLE 或 FAILED。FAILED 是整个页面和 Job 的系统级错误，不能做成某一家供应商的 badge。

规则：

- 不允许根据相似名称自动切换到另一个 supplier_id。
- ID 与名称冲突时不能继续展示该 ID 的等级。
- 第一版可以使用数据集内的 ID/名称表作为只读、版本化身份目录。
- 名称规范化只允许 Unicode NFKC、大小写归一、首尾空格删除和连续空格合并。
- 其他名称必须命中随 dataset version 冻结的 alias allowlist，否则进入 REVIEW_REQUIRED；禁止模糊匹配。
- 这不等于建立了企业级供应商主数据系统。

### 7.8 数据集生命周期与任务绑定

数据集必须先发布为不可变版本，再绑定任务。

建议新增 task_history_bindings，按 task_id 和 task_revision 保存：

- dataset_id。
- dataset_version。
- content_sha256。
- rating_method_version。
- identity_matcher_version 和 alias_allowlist_hash。
- scope 和 as_of_date。
- binding 状态。

运行规则：

- 创建任务时，根据受控 scope 映射原子绑定当时已发布的数据集；不适用时也保存明确的 OUT_OF_SCOPE binding。
- 需求、报价、人工校正或偏好 Apply 产生新 revision 时，默认原样复制上一 revision 的 binding。
- Graph、Job 和 Input Snapshot 保存 binding_id，不能只保存可变路径。
- Worker 只能读取任务绑定的版本和哈希，不能读取 latest 文件。
- Input Snapshot 和 Result 继续冻结实际使用的供应商聚合快照。
- 纯偏好 Scenario 必须沿用 baseline 的历史数据版本，不能顺便升级。
- 用户显式执行“刷新历史数据”时才绑定新版本、推进 task_revision 并全量重算。
- 刷新后旧 Result、Scenario、Intent、Conversation 和 Summary 标记 STALE，并 supersede 旧的活动 Job，但历史记录仍可查看。
- 迟到 Worker 结果不得覆盖当前 revision。

新增写接口：

    POST /api/v1/tasks/{task_id}/supplier-history/refresh

接口要求 Idempotency-Key、expected_task_revision 和目标已发布 dataset_version。它必须在一个事务中写入新 binding、推进 revision、记录 old/new 版本和 hash，并按当前正式报价排队全量重算。ABANDONED 任务拒绝该操作。

## 8. 付款条件方案

### 8.1 条件性决策字段

payment_terms 当前属于非关键展示字段，并会在 Reviewed 到 Rules 的入口被过滤。本次必须同时修改字段审核策略和规则集成边界。

建议新增 DECISION_CONDITIONAL 分类：

- 未选择付款排序时，缺失付款条件不改变报价的硬性可行性。
- 付款被选为主或次指标时，payment_terms 必须经过审核并传入规则引擎。
- 从其他偏好切换到付款偏好时，旧审核没有足够信息则 Scenario 本身仍可保存为 READY，但其 simulated comparison 返回 PENDING_INPUT 和 required_inputs。
- Apply 后执行全量重审和重算。

不能简单把 payment_terms 变成所有任务都必须填写的硬性字段。

### 8.2 第一版支持范围

第一版只比较起算事件一致且已确认的标准 Net N：

    Net 60 > Net 45 > Net 30 > Net 15

建议演示统一采用 invoice date 作为起算事件，并在报价或人工确认中提供证据。裸 Net 30 不能在规则中静默假定起算日。

### 8.3 PaymentTermEvaluation

建议包含：

| 字段 | 含义 |
|---|---|
| raw_text | 原始文本 |
| normalized_text | 规范文本 |
| payment_type | 第一版支持 NET_DAYS |
| net_days | 确认账期天数 |
| payment_start_event | INVOICE_DATE 等明确起算事件 |
| parse_status | 单份报价自身是否已解析并确认 |
| reason_codes | 不可比较原因 |
| evidence_refs | 原文或人工确认来源 |
| validation_status | 提取和审核状态 |
| normalization_rule_version | 规范化规则版本 |

以下情况第一版不可自动比较：

- 2/10 Net 30 等现金折扣。
- 分阶段付款。
- 部分或全部预付款。
- 信用证。
- 不同或未知的付款起算事件。
- 付款条件会改变交期起算语义。

如果测试承诺支持 Net thirty，必须实现有限词数的确定性解析器；不能仅依赖模型猜测。

单份报价可成功解析，不代表多份报价可以相互比较。当付款条件实际作为主指标或已触发的次指标时，规则引擎必须对当前候选组执行跨报价基准检查：

- 所有候选均有已确认的 net_days。
- 所有候选的 payment_start_event 相同。
- 任何起算事件不同或未知时，相关 CriterionEvaluation 为 INCOMPARABLE。
- ranking trace 写入 PAYMENT_BASIS_MISMATCH。
- ComparisonDisposition 返回 PENDING_INPUT。

## 9. 后端合同与排序实现

### 9.1 规则模型

建议增加或扩展：

- RankingCriterion。
- DecisionPreferencesV2。
- PaymentTermEvaluation。
- RateMetric，保存 numerator、denominator 和精确 rate。
- SupplierHistoryDatasetContext。
- SupplierHistorySnapshot。
- SupplierHistoryBinding。
- SupplierIdentityMatch。
- CriterionEvaluation。
- RankingTrace。

CriterionEvaluation 至少包含：

- criterion。
- status。
- exact_value。
- display_value。
- direction。
- reason_codes。
- evidence_refs。

SupplierEvaluation 保留 hard_status，并返回六个指标各自的 CriterionEvaluation。历史数据绑定属于任务输入，不属于用户偏好。

### 9.2 权威排序过程

规则引擎按以下流程返回结果：

1. 应用明确的供应商排除，并记录 original_scope_count 和 excluded_quote_ids。
2. INFEASIBLE 不进入候选排序。
3. 对 PENDING 执行决策影响判断；无法确定其不会改变选择时返回 PENDING_INPUT。
4. 付款和历史模式第一版对 hard PENDING 一律保守阻塞。
5. 对 FEASIBLE 候选检查主指标可比较性。
6. 根据主指标方向生成最佳组。
7. 如果主指标为成本且设置容差，以最低成本加容差形成最佳组。
8. 最佳组只有一个候选时停止，次指标标记为未触发。
9. 最佳组有多个候选时检查次指标，包括跨报价付款起算事件一致性。
10. 次指标可比较时进一步缩小最佳组。
11. 最佳组仍有多个候选时返回业务并列。
12. quote_id 仅用于稳定显示，不能打破业务并列。

### 9.3 RankingTrace

Comparison Result 必须返回权威 trace：

- ordered_criteria 和排序方向。
- 每个候选的精确值、显示值和可比较状态。
- 每轮排序前后的候选组。
- 成本容差是否应用。
- secondary_applied。
- tie_group。
- blocker reason codes。
- comparison_disposition。
- original_scope_count 和 excluded_quote_ids。

前端、Summary 和 Conversation 只能基于该 trace 解释“为什么这样排”，不得自行重算赢家。

### 9.4 ComparisonDisposition

继续使用现有公开合同，不另建含义重叠的 recommendation_status：

| 状态 | 含义 |
|---|---|
| RECOMMENDATION_AVAILABLE | 可以发布确定性推荐或业务并列 |
| PENDING_INPUT | 缺少会影响当前选择的事实 |
| NO_FEASIBLE_QUOTES | 没有满足硬性要求的报价 |
| EMPTY_SCOPE | 没有可比较范围 |

如果是用户排除导致范围为空，仍返回 EMPTY_SCOPE，同时在 comparison reasons 和 ranking trace 中写入 ALL_CANDIDATES_EXCLUDED、original_scope_count 和 excluded_quote_ids，以区别于任务本来没有报价。

Loader、Schema、哈希或运行错误通过 Job FAILED 和现有错误信封返回，不创建一个 disposition=FAILED 的成功 Comparison Result。

### 9.5 数据集 Loader

Loader 必须：

- 只访问受控数据根目录。
- 按 dataset_id、version 和 hash 精确读取。
- 校验 JSON Schema、内容哈希、供应商 ID 唯一性和计数关系。
- 校验 rate 与 numerator/denominator 一致。
- 重新验证 overall_grade。
- 区分 NO_DATA、OUT_OF_SCOPE、INSUFFICIENT_SAMPLE 和 DATASET_UNAVAILABLE。
- 文件损坏或哈希不符时使 Job 失败，不返回空数据。

### 9.6 Selection Gap 与 Decision Impact

新增指标不能复用只面向成本的差距语义：

- 成本：继续展示确认成本差和现有确定性影响判断。
- 交期：展示日期或天数差，不虚构可行的供应商承诺。
- 付款：只有起算事件一致且均可比较时，才能说明“至少需要 Net X 才能并列”；否则只建议补充付款证据。
- 历史等级、准时率和拒收订单行率：属于冻结历史事实，不生成“要求供应商立即提高历史指标”的沟通建议。
- 历史指标未入选时，只解释其对当前排序的影响，并提供可执行动作，例如更换偏好、明确排除，或在管理员发布适用数据集后执行显式刷新。
- 尚未实现并验证 dominance proof 的付款或历史模式，hard PENDING 一律阻塞正式推荐。

Selection Gap 和 Decision Impact 必须记录 schema version、rule version、input hash 和 result_id。新结果将其保存为冻结 artifact；旧结果没有对应 artifact 时显示“当时未记录”，不得使用当前代码现场补算历史解释。

## 10. Workflow、Scenario、Summary 和聊天

### 10.1 Workflow 冻结

在进入比较节点前：

1. 读取当前 task revision 的历史数据绑定。
2. 校验 scope 和内容哈希。
3. 使用 binding 中冻结的 identity_matcher_version 和 alias allowlist 完成供应商身份匹配，并按 quote/version 持久化 match artifact。
4. 生成任务专用历史快照。
5. 将付款评估和历史快照传入纯规则引擎。
6. 将有效偏好、数据集上下文、供应商指标和 ranking trace 写入 Input Snapshot 与 Result。
7. 将 Selection Gap、Decision Impact 和 Policy Compliance 的确定性输入、输出及 evaluator version 保存为冻结 artifact。

等待模型或用户时不持有数据库事务或锁。

历史结果只能读取自己的冻结 artifact。旧 Result 缺少某类 artifact 时显示“当时未记录”，不得使用当前算法或当前制度重新生成后补。

### 10.2 Scenario 两次确认

保留当前安全流程：

1. LLM 或表单生成 Proposal。
2. 用户确认 Proposal 后只生成 READY Scenario，不推进 task revision。
3. 如果切换到付款偏好且报价付款字段尚未审核，Scenario 仍可为 READY，但 simulated.comparison.disposition 必须为 PENDING_INPUT，并列出 required_inputs。
4. 用户再次点击 Apply。
5. Apply 校验 expected revision、baseline hash 和幂等键。
6. Apply 推进 task revision、写入新 Decision Profile 并排队全量重算。
7. Worker 进入现有 WAITING_INPUT/报价审核流程，用户确认 payment_terms 和 payment_start_event 后继续同一个 Graph 并重算。

历史数据版本默认沿用 Scenario baseline。更换历史数据集必须是单独、明确的刷新操作。

### 10.3 自然语言映射

LLM 继续允许两类经过批准的结构化变更：

| 类别 | 字段 |
|---|---|
| 硬性需求模拟 | budget_amount、delivery_deadline |
| 决策偏好 | primary_criterion、secondary_criterion、excluded_supplier_ids、cost_tolerance_amount |

本次只迁移旧 ranking_mode，不删除已有的预算和交付截止日期模拟能力。

“供应商表现优先”存在综合等级、准时率和拒收订单行率三种解释，模型必须补问，不能擅自默认。

聊天不能提出权重、第三排序项或未批准的自定义指标。

### 10.4 LLM 事实校验

Summary 和 Conversation 的冻结事实白名单增加：

- payment_start_event 和 net_days。
- 历史等级。
- 准时率的分子、分母和比例。
- 拒收订单行率的分子、分母和比例。
- 样本量和统计期间。
- dataset_version、content_sha256 和 rating_method_version。
- ranking trace 和 ComparisonDisposition。

模型虚构或串用其他版本的数值、等级、样本量、供应商或赢家时，后端必须拒绝响应并记录失败；不能静默回退为看似正常的叙述。

模型只接收当前任务冻结的聚合事实，不接收 1,185 条原始采购记录。

## 11. RAG 边界

供应商历史数据属于结构化业务事实，不进入制度 RAG。

RAG 仍只负责检索制度条款。未来若制度条款包含“过去 12 个月准时率至少 95%”，只有当历史快照使用同一 as-of 和 12 个月窗口时，规则引擎才能执行比较。

当前全期间聚合不能冒充过去 12 个月数据。

本次比赛版不增加结构化制度阈值执行，因此历史表现只影响采购排序，不改变现有“供应商合规仍需单独核验”的边界。

## 12. 新增“供应商信息”页面

### 12.1 页面定位

页面名称：供应商信息  
建议路由：/tasks/:taskId/suppliers

该页面定位为：

> 当前采购任务的供应商决策画像。

它只读展示当前任务中已正式提交、并纳入当前或历史比较范围的供应商和报价。QuoteDraft 与已停用报价不进入页面 KPI、图表或排序，可以单独显示数量并链接到报价页处理。

它不是全局供应商档案库，也不提供供应商 CRUD、审批或联系能力。

将它放在任务工作台“报价与证据”和“决策结果”之间，帮助用户在查看或调整排序时快速理解本次候选供应商。首次分析前也可以打开，但只展示当时已经具备的报价与历史绑定信息。

后续如果建设可信供应商主数据和权限体系，再单独规划全局 /suppliers 页面；本次不提前伪造该能力。

### 12.2 页面状态与数据上下文

页面必须具有三个互斥状态：

| view_state | 触发条件 | 允许展示 |
|---|---|---|
| QUOTE_ONLY | 未传 result_id，且 task.current_result_id 为空 | 当前正式、active 报价的已审核事实，以及当前 revision 的历史数据绑定预览 |
| CURRENT_RESULT | 未传 result_id 时读取 task.current_result_id，或显式 result_id 等于该指针 | 当前 Result 冻结的报价、评估、历史快照、trace 和衍生产物 |
| HISTORICAL_RESULT | 显式 result_id 不等于 task.current_result_id，即使两者 revision 相同 | 只展示该 Result 当时冻结的报价版本、快照和衍生产物 |

QUOTE_ONLY 中 hard status、CriterionEvaluation、ranking trace、selection gap 和 policy assessment 可以为空，并返回明确的 NOT_RUN 或 NOT_RECORDED 原因。不得拿上一 revision 的 Result 填充当前页面。

QUOTE_ONLY 的 snapshot_context.kind 为 TASK_REVISION_BINDING，表示使用当前 revision 的正式报价和历史 binding，并不伪装成已经存在 Input Snapshot 或 Result。

比较 Job 正在运行只是 QUOTE_ONLY 的进度说明；Summary 或 Conversation 等其他 Job 运行不能把已有 CURRENT_RESULT 降级为 QUOTE_ONLY。

旧 Result 没有历史快照或某类衍生产物时，整块显示“该版本当时未记录”，不得回查最新数据补齐。

页面顶部优先显示业务友好的上下文：

- 当前第 N 版或历史第 N 版。
- 商品范围，例如 Electronics / Microcontroller MCU-9。
- as-of 日期和统计期间。
- 合成演示数据标识。
- QUOTE_ONLY、CURRENT_RESULT 或 HISTORICAL_RESULT 状态。

dataset ID、版本、hash、rating method version、内部 result_id 和 snapshot_id 放入“数据来源与版本”折叠区，不在主界面堆叠技术标识。

在 QUOTE_ONLY/CURRENT_RESULT 中，dataset_status=FAILED 或 hash mismatch 是整个页面的系统级错误：页面顶部显示失败，停止展示任何历史百分比和等级。

HISTORICAL_RESULT 只校验该 Result 自己冻结的 snapshot/artifact。只要冻结内容存在且哈希自洽，即使今天的发布文件已删除或 Loader 配置变化，也必须继续展示历史值；只有冻结 artifact 自身缺失或损坏才报错。历史结果模式严禁读取最新评级补齐页面。

### 12.3 页面布局

建议采用三层布局。

第一层：概览与筛选

- 有效报价数。
- 已匹配供应商数。
- 待确认数。
- 历史不可用数。
- 按供应商名称、ID 搜索。
- 按硬性状态、历史等级和数据状态筛选。

FEASIBLE/PENDING/INFEASIBLE 和 INSUFFICIENT_SAMPLE/NO_DATA/OUT_OF_SCOPE 使用紧凑筛选 chips，不做成大量 KPI 卡。

第二层：供应商概览和可视化

- 左侧为供应商列表或紧凑卡片。
- 右侧为表现散点图。
- CURRENT_RESULT/HISTORICAL_RESULT 下方显示本次报价多指标小图。
- QUOTE_ONLY 不显示多指标比较图、排名高亮或推荐暗示，只显示“确定性比较尚未运行”；不得由前端根据字段自行拼出确认总成本、预计到货或排名。

第三层：所选供应商详情摘要

- 身份、适用范围和历史核心指标。
- 当前报价摘要。
- 当前任务差距与数据不确定性摘要。
- 报价证据、制度检查和版本记录的状态、计数及深链。

本页不复制完整决策页、制度页、证据抽屉和审计时间线。

### 12.4 页面实体粒度

- 历史表现和散点图按已确认 supplier identity 聚合，一家供应商只显示一个历史气泡。
- 报价事实、硬性可行性和排名按 quote_id 与 quote_version 组合标识。
- identity_match_status=MATCHED 时按冻结的 supplier_identity_id 分组，每组嵌套 quotes 列表。
- REVIEW_REQUIRED 或 CONFLICT 时不得按上传者声明的 supplier_id 合并；每个 quote_id/quote_version 独立显示为“身份待核验候选”。
- 顶部分别返回 matched_supplier_count、unresolved_identity_quote_count 和 quote_count，不能混用。
- 演示数据原则上一家供应商只有一个 active 逻辑报价，但后端必须正确处理同一 supplier_id 的多个 quote_id 及各自多个 quote_version。
- 历史模式使用冻结的 supplier binding 合并 supplier_id，前端不得从当前 Task 报价列表反查历史身份。

### 12.5 图表一：历史表现气泡散点图

设计：

- 横轴：历史准时率，越右越好。
- 纵轴：历史拒收订单行率，越低越好。
- 气泡大小：min(valid_delivery_order_line_count, valid_quality_order_line_count)，表示保守有效样本。
- 颜色和字母：A、B、C、D。
- 引导文字：右下方向表现更优。
- 坐标从 0% 开始，Y 轴按正常方向向上增长，并明确标注“拒收订单行率越低越好 / 右下更优”。
- 只显示评级阈值虚线，不允许前端根据象限重新计算或着色等级。
- 气泡面积采用受限的平方根比例，并提供尺寸图例，避免大样本在视觉上过度压制小样本。

Tooltip 同时显示：

- 供应商名称和 ID。
- 等级。
- 准时分子、分母和比例。
- 拒收分子、分母和比例。
- identity match status。
- as-of、统计期间和数据集版本。

只有 MATCHED 且历史指标可用的供应商进入散点图。N、NO_DATA、OUT_OF_SCOPE 和身份冲突不能用 0 值伪造坐标，应列入图旁的“暂无可比历史”区域。

QUOTE_ONLY 只有在当前 task revision 已持久化 identity match artifact、matcher_version 和输入 hash 时才可显示带“预览、尚未用于正式结果”标识的散点；否则该区域显示“身份与历史表现待分析”。

grade 一律使用后端冻结值。图表点击后联动供应商详情；键盘用户也必须可以选择并看到可见焦点。页面同时提供等价数据表，详情更新使用适当的 aria-live 提示，颜色不能是唯一编码。

### 12.6 图表二：当前报价指标比较

使用独立量纲的小型横向点图或条图，分别展示：

- 已确认总成本，越低越好。
- 预计到货日期，越早越好。
- 已确认 Net 天数，越长越好。
- 历史准时率，越高越好。
- 历史拒收订单行率，越低越好。
- 综合历史等级。

图表规则：

- 总成本只有同一币种且值已确认时才进入同一坐标轴。
- 到货使用日期轴，并绘制采购交付截止线，不转换成无定义的分数。
- Net 天数只有 payment_start_event 一致且 CriterionEvaluation=COMPARABLE 时才进入同一坐标轴。
- 准时率和拒收订单行率只展示各自达到样本门槛的值。
- 综合等级使用离散 badge 或阶梯，不伪装成连续分数。
- MISSING、INCOMPARABLE、INSUFFICIENT_SAMPLE 和 OUT_OF_SCOPE 显示状态，不以 0 落点。
- 主、次指标高亮以及“次指标已触发”完全读取 ranking trace，前端不得自行判断。

未选择的指标明确标记为“仅展示”。

不同单位不能合并成一个未经定义的综合分，因此不使用雷达图，也不显示虚构的 0–100 总分。

### 12.7 供应商列表

每行建议展示：

- display_name（来自报价）和 supplier_id。
- identity_match_status；只有 MATCHED 才显示“与版本化历史目录匹配”。
- 当前模式显示 active 报价，历史模式显示“当时纳入比较”的冻结报价。
- 报价版本及审核状态。
- 硬性可行性。
- 确认总成本、预计到货和付款条件。
- 带上下文的历史标识，例如“MCU-9 历史等级 A · 55 行 · v1”。
- 身份匹配状态。
- 进入报价证据、决策矩阵或制度检查的链接。

不要只显示裸的 “[A] Supplier”。评级必须始终带商品范围、样本量和版本语境。

### 12.8 供应商详情摘要

当前报价摘要：

- 业务界面默认显示报价版本；quote_id 放在可复制的技术详情中。
- 当前模式显示 active 状态，历史模式只显示 in_scope_at_result，不读取今天的 active/current_version。
- 制造商、料号和封装。
- 分别显示采购需求数量、报价 MOQ/订购步长和规则导出的实际采购量。
- 单价、费用和确认总成本。
- 到货承诺、预计到货和截止日期。
- payment_terms、规范账期和起算事件。
- 报价日期和有效期。
- evidence summary 使用后端定义的 required_field_count、required_verified_count、evidence_source_count 和 review_status；前端不自行计算“完整率”。

历史表现部分：

- 数据范围和统计期间。
- 综合等级和样本量。
- 准时率原始计数及比例。
- 拒收订单行率原始计数及比例。
- N、低样本或身份冲突说明。

当前任务影响摘要：

- 当前 hard_status。
- 主、次指标的 CriterionEvaluation。
- 未入选原因、未知项影响和建议沟通策略的简短摘要。
- 当前 ranking trace 中该供应商的路径。
- 完整差距、沟通建议和证据通过深链打开原页面。

制度部分：

- CURRENT_RESULT/HISTORICAL_RESULT 只显示同一个 Result 冻结的制度核验状态摘要；QUOTE_ONLY 显示 NOT_EVALUATED。
- 制度引用通过深链进入制度页，不在本页重复全部内容。
- 不得把历史等级写成合规、认证、在约或批准状态。

历史模式默认只展示该 Result 冻结的报价版本和原件。完整版本历史若需要展示，只能作为明确分离的“当前审计历史”链接，不能混入历史 snapshot。

当前没有可信数据支持以下内容，因此页面不能推断或虚构：

- 企业注册和真实认证。
- 制裁、新闻或财务风险。

- 跨任务采购金额和中标率。

### 12.11 只读聚合 API

建议新增：

    GET /api/v1/tasks/{task_id}/suppliers
    GET /api/v1/tasks/{task_id}/suppliers?result_id={result_id}

这是任务级只读 View API，不建立供应商主数据写模型。

响应至少包含：

- schema_version、task_id、snapshot_revision、result_id 和 view_state。
- is_current、snapshot_id、context_sha256 和 data_availability。
- history dataset context 和 dataset_status。
- matched_supplier_count、unresolved_identity_quote_count 和 quote_count。
- QUOTE_ONLY/CURRENT_RESULT 可返回当前 draft_count 和 inactive_quote_count。
- HISTORICAL_RESULT 未冻结上述两个计数时返回 null 和 NOT_RECORDED；不得查询今天的值混入历史 snapshot。若产品确需当前导航计数，应放在明确分离且不参与 context_sha256 的 live_task_navigation 区域。
- effective preferences 和 ranking trace 摘要。
- 每个供应商独立的 identity_match_status 和 history_availability_status。
- MATCHED 项按 supplier_identity_id 分组的 quotes 列表，以及不合并的 unresolved_identity_quotes。
- 当前或冻结 quote 信息；历史信息包含 in_scope_at_result、冻结 document ID/hash 和 is_synthetic。
- hard status 和六个 CriterionEvaluation。
- history snapshot。
- policy assessment。
- evidence summary。
- selection gap、未知项影响和沟通建议摘要。

同一 supplier_id 可能有多个逻辑 quote_id，每个 quote_id 又可能有多个 quote_version。响应和深链必须保留三层关系，推荐深链格式为：

    /tasks/{task_id}/suppliers?result_id={result_id}&quote_id={quote_id}

接口规则：

- 未传 result_id 且当前 revision 没有 Result 时返回 QUOTE_ONLY，不回退旧 Result。
- 未传 result_id 且 task.current_result_id 存在时返回该指针对应的 CURRENT_RESULT；不能仅凭 revision 猜测 current。
- 显式 result_id 只有等于 task.current_result_id 才是 CURRENT_RESULT，其他合法结果均为 HISTORICAL_RESULT。
- 传入 result_id 时必须校验该结果属于同一 task 和 owner；未知、跨任务或越权统一返回 404。
- 历史模式完全使用该 Result 的冻结快照，不能读取当前 active/current_version。
- supplier_id 必须通过该 Result 冻结的 quote-to-supplier binding 合并；前端不得从当前 Task 报价列表补历史 supplier_id。
- 旧 Result 缺 V2 字段时返回 nullable 值和 NOT_RECORDED，不回查 latest。
- Selection Gap、Decision Impact 和 Policy Compliance 只能返回同 Result 的冻结 artifact。
- 历史页进入决策、制度、证据或审计页面的深链必须携带并校验 result_id 和 quote_id。决策使用 /tasks/{task_id}/results/{result_id}?quote_id={quote_id}；其他目标页增加等价的 result_id 查询参数。
- 历史目标页找不到对应冻结 artifact 时显示“当时未记录”，绝不能 fallback 到 current result。
- 公开响应只返回逻辑 source ID 和 hash，不暴露 storage_path、受控根目录或原始历史行。
- 历史响应的 ETag 可由 snapshot/context hash 派生。
- 前端查询缓存键必须包含 task_id、result_id 和 view_state。

## 15. 测试方案

### 15.1 数据生成和发布

- 从 data/source/purchase_orders.csv 精确筛选 Electronics / Microcontroller MCU-9 的 1,185 条记录。
- 输入乱序后 canonical 输出保持一致。
- 固定显式生成时间后，同一输入产生字节相同的 JSON。
- 记录 source hash、output hash、generator version、scope 和阈值。
- manifest hash 和数据内容 hash 均被任务绑定并可复核。
- 测试重复 PO、非法日期、缺失日期、未来记录和非法布尔值。
- 测试供应商 ID 重复、ID/名称冲突和 schema 损坏。
- 测试 n=0 为 NO_DATA，以及 n=6、9、10 的 N/可比较边界。
- 测试 delivery/quality 两个有效分母不同的场景。
- 测试 90%/2%、80%/5%、70%/10% 阈值边界。
- 用精确分数验证四舍五入后相同但实际比例不同的排序。
- 四家演示供应商聚合值与第 7.6 节一致。

### 15.2 付款

- N30、Net30 和 Net 30 规范化。
- 若承诺 Net thirty，则验证确定性词数解析。
- Net 15/30/45/60 正确生成 net_days。
- 任意 Net 天数只要起算事件不同就不可比较，并产生 PAYMENT_BASIS_MISMATCH。
- 折扣、预付款、信用证和分期付款不可自动比较。
- 空值不等于 Net 0。
- 人工纠正保留原提取值和证据链。
- 付款未被选择时不改变硬性可行性。
- 切换为付款偏好时，未经审核字段产生 PENDING_INPUT。

### 15.3 排序引擎

- 六种原子指标分别产生预期顺序。
- 表驱动覆盖所有合法主、次组合。
- 主指标未并列时不读取次指标决定赢家。
- 主指标并列时才应用次指标。
- 主、次均相同返回并列组。
- quote_id 不打破业务并列。
- 不可行和已排除报价不进入候选集合。
- 主指标缺失阻塞唯一推荐。
- 次指标只在主指标最佳组内检查缺失。
- 未选指标缺失只提示。
- hard PENDING 在付款和历史模式下保守阻塞，不能被排序过滤掉。
- N、NO_DATA、OUT_OF_SCOPE、DATASET_UNAVAILABLE 和身份冲突分别处理。
- 成本容差与每个合法次指标组合均有测试。
- 输入顺序变化不改变业务结果。
- 改善某项指标不会让该供应商在该指标排序中变差。

### 15.4 Workflow、版本和并发

- Job 绑定明确的 dataset version 和 content hash。
- 运行期间替换 latest 文件不改变当前 Job。
- 数据集显式刷新推进 task revision。
- 刷新接口验证 Idempotency-Key、expected revision、目标发布版本和 ABANDONED 拒绝。
- 纯偏好 Scenario 沿用 baseline 历史版本。
- 数据集刷新后旧 Scenario 不可静默应用。
- 旧 Result、Summary 和 Conversation 继续使用冻结快照。
- Selection Gap、Decision Impact 和 Policy Compliance 使用同 Result 的冻结 artifact，旧结果缺失时不现场补算。
- 迟到 Worker 结果不能覆盖新 revision。
- 旧四种 ranking_mode 的 Profile、Scenario、Intent 和 Message 可读取。
- Scenario Proposal、Confirm 和 Apply 两次确认流程保持不变。
- 幂等键、expected revision 和 409 契约保持有效。
- PostgreSQL 和 SQLite 行为一致。

### 15.5 LLM

- 六个枚举的自然语言映射。
- budget_amount 和 delivery_deadline 的现有自然语言模拟能力不回退。
- “供应商表现优先”触发澄清，不擅自选择三级指标之一。
- 非法枚举和混合新旧载荷被拒绝。
- 模型虚构等级、百分比、样本量、账期或赢家时校验失败。
- 模型只能引用冻结版本，不得引用 latest 数据集。
- 上传文档中的 prompt injection 不改变排序和工具权限。
- 固定模型和真实模型测试结果明确区分。

### 15.6 供应商信息页

- 当前模式和历史模式的数据源严格分开。
- QUOTE_ONLY、CURRENT_RESULT 和 HISTORICAL_RESULT 三种状态分别验收。
- QUOTE_ONLY 不回退旧 Result，运行中字段显示 NOT_RUN/NOT_RECORDED。
- CURRENT_RESULT 只由 task.current_result_id 判定；同 revision 的其他 Result 仍按历史模式展示。
- QUOTE_ONLY 不显示指标比较图、排名高亮或前端推导值。
- 草稿和已停用报价不进入 KPI、散点或排序。
- matched_supplier_count、unresolved_identity_quote_count 与 quote_count 独立。
- 未确认身份的重复声明 supplier_id 不合并；MATCHED 身份可以分组并保留多个 quote_id。
- 历史模式不读取当前 active/current_version，使用 in_scope_at_result 和冻结文档身份。
- 页面所有卡片和图表来自同一个 snapshot context。
- N、NO_DATA、OUT_OF_SCOPE 和身份冲突不产生伪造的 0 坐标。
- 散点 tooltip 展示分子、分母、比例、期间和版本。
- 图表具备键盘操作和文本/表格替代。
- 颜色不是唯一状态提示。
- 未选指标清楚标记为仅展示。
- 旧 Result 缺少新字段时显示“当时未记录”。
- 外部、跨任务或越权 result_id 统一返回 404，响应不暴露磁盘路径。
- 历史深链携带 result_id/quote_id，目标页面不得回退 current result。
- 历史页不混入今天的 draft/inactive 计数；当前发布文件故障不影响哈希自洽的冻结历史 artifact。
- 系统级 dataset FAILED 时停止所有历史指标展示，不降级成逐供应商 N。
- 制度状态与历史等级不会被合并为同一结论。
- 深链能正确打开对应 quote_id 的证据。

### 15.7 人工端到端

- 四个主维度分别改变首选供应商。
- 准时率和拒收订单行率两个专项排序正确。
- 精确并列任务真实触发次指标。
- 复杂付款得到 PENDING_INPUT 和可执行的审核入口。
- 无历史和低样本状态有清晰说明。
- 数据集损坏导致显式 FAILED。
- 用户可以从供应商信息页进入报价证据、决策矩阵和制度检查。

13. 供应商信息页能快速展示当前任务供应商的报价摘要、适用范围内的历史表现、当前任务差距与未知项、证据入口和冻结版本。

16. Summary 和 Conversation 对付款、评级、比例、样本量和赢家执行冻结事实校验。

    固定且版本化的 MCU-9 合成历史数据
    + 可重复评级生成器

    + 六个原子指标
