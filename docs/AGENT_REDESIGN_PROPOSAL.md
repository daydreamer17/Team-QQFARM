## 1. 新版 Agent 的定位

**Agent 是采购比较流程中的“查证与解释助手”。**

采用“固定主流程与门禁 + 局部自主调查”的设计：程序保证步骤、计算与权限正确；Agent 根据问题对决策的影响确定调查优先级，制定计划，选择工具，根据证据调整下一步，并在明确的停止条件下结束调查。

| 分工 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 确定性程序 | 字段校验、采购量、成本、交付判断、可行性、排序、影响与差距计算、版本与审批门禁 | 自由解释模糊制度 |
| Agent | 根据影响组织调查、定位原文、按需检索制度、集中澄清、解释改善条件与更新影响 | 编造报价事实、修改硬约束、批准采购、下单 |
| RAG | 从用户已发布的制度知识库检索适用条款，提供可追溯引用 | 计算成本、证明供应商实际符合制度 |
| 用户 | 确认输入、处理真实疑点、管理制度、决定是否调整需求及批准结果 | 逐条重复审核已经确认且未变化的字段 |

Agent 的价值应体现在常见问题上：**为什么没有选更便宜的供应商？报价中的附加条件是否影响比较？这笔采购适用哪项制度？更新报价后原结论还能否使用？**

不为了展示 Agent 而强制补问、强制检索或增加重复审核。

核心投入按优先级为：**① 决策影响分析 → ② 有计划、可调整、可停止的自主调查 → ③ 入选差距与条件试算。** 数值与边界由程序计算，Agent 负责调查策略及行动建议。

## 2. 相比旧方案的调整

| 旧设计倾向 | 新版设计 |
| --- | --- |
| 当前 main 在绑定制度且允许最终推荐时固定检索三类控制码；本地另有要求级全条款编排 | 按业务范围确定必查清单，再按实际疑问调查；必查事项由程序保证，Agent 不能自行跳过 |
| 把资质核验作为每次流程的必经阶段 | 当前以采购需求和报价为主要输入；没有真实资质资料时，不声称已核验 |
| 逐个问题、逐个字段修改 | 集中展示可发现的问题，支持批量修改、统一提交与重新校验 |
| 依靠 Agent 审核所有已填写字段 | 常规合规性由表单和后端校验；Agent 只处理需要查证的疑点 |
| 任何未知字段都阻塞整个任务 | 先计算对推荐的影响；已证明不影响的未选报价保留未知，但不阻塞当前推荐 |
| 用户提问后选择一个工具回答 | 支持系统主动触发调查，按目标、计划、观察结果调整工具调用并停止 |
| 只说明供应商为何被排除 | 同时说明成为可行候选及成为优选分别还差什么，提供有条件的协商建议 |
| 用补证卡片作为主要前端交互 | 主要提供结构化表单、知识库管理、必要的澄清卡片及工具调用记录 |
| 将最终摘要也做成独立 Agent | 固定摘要模板 + LLM 表达，结果与数字必须来自程序 |

本方案是新目标，不代表上述能力已实现，也不代表旧计划文件已同步修改。实施时需同步 [WEEK2_PLAN.md](WEEK2_PLAN.md) 与 [WORKFLOW.md](WORKFLOW.md)。

### 2.1 最新 main 提供的实现基础

- 制度 PDF／TXT 上传、读取解析草稿、人工修改条款、发布与索引已有后端接口；发布后的内容不可直接修改。
- 创建任务支持 `policy_binding`，固定制度集合、索引版本、类别与地区；结果接口提供本次制度检索记录与引用。
- LangGraph 已包含 `retrieve_policies`、`await_policy_evidence_review`、`publish_final_result`，制度检索异常可以暂停并通过受控回答恢复。
- 已有门禁验证制度证据检索是否成功，不代表已完成供应商准入、RoHS 事实核验或金额审批执行。

新版重点是在这些基础上接入调查 Agent，而不是重新开发一套上传或工作流系统。

## 3. 从输入到结果的主流程

```text
用户手动填写 / 上传文件自动解析
                ↓
统一结构化表单：填写提示 + 后端完整校验
                ↓
集中展示问题 → 批量修改 → 统一提交 → 确认并冻结输入版本
                ↓
程序计算采购量、成本、交付、可行性、初步排序及未知信息的影响
                ↓
按需进入 Agent 调查：目标 → 计划 → 工具 → 观察 → 调整 → 停止
  优先处理影响决策的问题；查原文、查已有记录、按需查制度、集中补问
                ↓
获得确认的新事实 → 程序重算；输出入选差距与条件改善建议
                ↓
程序检查当前版本与必查事项；复用制度检索、异常暂停及受控发布
                ↓
生成比较结果与有来源的 Summary
                ↓
用户确认或审批；报价/需求更新则重算并重新确认
```

影响推荐的未知或冲突可以由系统主动触发调查，无需等待用户提问；没有查证需求时可以直接生成结果。用户也可针对当前结果主动提问。

### 3.1 输入与审核边界

- 手动填写与文件解析使用同一字段契约，而不是按照测试参考答案填写。
- 前端及时提示格式、范围、必填项；后端再次执行完整校验，不能只相信前端。
- 字段契约允许缺失的事实应支持显式“未知”状态，不要求用户猜值才能提交。结构必填、有效格式与用于最终采购的事实完整性分别校验；非候选报价的合法未知可进入初步比较。
- 批量校验集中返回当前可发现的问题。用户一次修改多个字段后统一提交；新修改引入的新问题仍可能需要再次处理。
- 已确认字段没有变化、没有新增冲突时，不重复要求审核。
- “金额不是数字”是字段错误；“有效报价超过采购预算”是不可行方案，两者不能混为一谈。
- 用户正常填写也不等于事实一定真实。没有原文或其他证据，Agent 不能凭空发现填写错误。
- 原文存在条件费用、相互矛盾的描述等真实疑点时，才调用查证或澄清工具；保留具体文件名、页码或定位信息，不要求前端展示整张图片。

## 4. 用户自主上传的制度知识库

### 4.1 存什么

用户上传企业制度、采购规范及合规要求，作为 RAG 知识库。它们回答的是“应该满足什么要求”，不是“供应商已经满足了这些要求”。

建议分类：

| 类别 | 示例内容 |
| --- | --- |
| 供应商准入 | 什么情况下需要使用批准供应商、何时需要例外审批 |
| 产品合规与材料要求 | RoHS 等要求的适用范围、可接受的证明材料类型 |
| 交付与采购条件 | 交付承诺、运费责任、采购条款的要求 |
| 审批与授权 | 金额对应的审批层级、特殊采购的授权要求 |
| 变更与重新评估 | 报价、需求、交付条件变化后是否需要重新确认 |

常规报价必填字段由上游字段契约负责，不作为每次下游 RAG 的固定检索任务。

### 4.2 上传不等于立即生效

知识库管理流程：**上传 → 解析与切分 → 预览 → 确认分类、适用范围、有效期与版本 → 发布 → 建立索引。**

- 当前上传 API 已支持 TXT 与可提取文本的 PDF，以及条款草稿读取、替换审核和发布；Markdown manifest 导入属于已有另一入口，不表示上传 API 已支持 Markdown。
- 复用这套接口建设前端预览、分类、范围与版本确认界面；自动判断不同版本的制度矛盾、提示并解决冲突仍需补充。
- 扫描 PDF 的 OCR 保持实验能力，解析不清楚的内容不得直接发布为可靠制度。
- 复用现有文档记录、哈希、幂等、修订检查及发布后不可变约束；具名用户/组织授权和多用户知识库隔离仍需完善，不能把当前测试身份当作完整权限系统。
- 同一制度存在冲突版本时，应提示并确认生效版本，不能由模型自行选择最方便的条款。
- 延用现有 PostgreSQL + pgvector，不因本方案另换向量库。
- 当前任务绑定与快照已固定制度集合、索引、类别和地区。沿用该机制；改变制度内容或索引后应创建绑定新版本的新任务，不能在旧任务里静默切换。前端需明确展示该行为。
- 上传内容只能作为检索资料，不能作为指令控制 Agent 或扩大其权限。

**自然语言制度不能直接成为执行规则。** 如需让“超过某金额必须审批”成为发布门禁，应经过人工确认，转成版本化的结构化规则，再由程序执行。

### 4.3 如何召回

上游无需传制度原文，只需传业务上下文，例如采购类别、地区、金额、相关报价事实和当前问题；制度已经在知识库中。

程序按上下文限定已授权、生效的知识库范围；Agent 针对实际疑问生成检索请求。保留现有混合检索与重排能力，但不再默认逐一召回全部条款。

检索返回：相关条款、适用范围、文档名、版本、原文位置与引用标识。回答必须关联这些来源。

必查事项不能由 Top-K 是否召回来决定：其清单来自已发布的规则目录。找不到证据时明确标注“制度依据不足”；不能自动判定通过，也不能误报成用户报价字段填写错误。

### 4.4 当前固定检索如何过渡到新版

当前 main 的行为：比较结果允许最终推荐且任务完整绑定制度时，固定检索 `APPROVED_SUPPLIER`、`ROHS_COMPLIANCE`、`AMOUNT_APPROVAL`。任一检索状态非 `OK` 会创建 `POLICY_EVIDENCE_REVIEW`，暂停当前结果发布。

未绑定制度的任务会跳过制度检索；比较结果不允许最终推荐时也跳过。**“跳过”只代表未做这一步，不代表制度适用性或供应商合规已通过。** 这是一项当前兼容行为，新版正式场景需明确是否要求绑定制度；需要制度门禁的任务由后端检查绑定，不允许 Agent 自行省略。

过渡方式：保留检索 artifact、引用校验、版本检查和发布节点；将固定三个控制码替换为程序依据业务范围及已确认规则生成的必查清单。Agent 可以围绕清单中的疑点继续调查，并对用户问题按需检索，但不能用一次自由 Top-K 搜索代替必查覆盖。

现有 CLI 的有引用 LLM 制度解释可以复用；仍需接入任务上下文和工具接口，不能把独立 CLI 已可用等同于前端聊天或自主调查已经完成。

## 5. 要实现的 Agent 功能与工具

下表中的工具名是拟议接口，不表示已经全部存在。现有计算、来源及检索能力优先封装复用。

| 功能 | 可自主选择的工具 | 边界 |
| --- | --- | --- |
| 判断未知信息是否影响推荐 | `analyze_decision_impact` | 程序计算成本边界与决策影响；不能凭模型感觉跳过问题 |
| 解释为何选或不选某供应商 | `get_comparison_result`、`get_cost_breakdown` | 读取程序结果，不重新让 LLM 算金额或排序 |
| 查明报价条件及字段出处 | `locate_quote_source` | 只读取本任务授权文件；找不到则承认未知 |
| 查找已有的确认信息 | `get_confirmed_quote_records` | 只查本任务实际已有且适用于当前报价、交付地点等条件的记录；记录不存在则明确返回未找到 |
| 回答适用制度问题 | `retrieve_policy` | 限定用户、业务范围与制度版本；回答附来源 |
| 调查制度检索异常 | `get_policy_retrieval_status`、`retry_policy_retrieval` | 拟封装已有检索记录与恢复机制；重试预算及授权由程序控制，不修改冻结的制度版本 |
| 组织必要的澄清 | `request_clarification` | 集中展示疑点与核对位置，不重复询问已解决问题 |
| 解释新旧报价变化 | `compare_quote_versions` | 区分字段变化与结果变化；重算由程序负责 |
| 分析成为候选或优选还差什么 | `analyze_selection_gap` | 程序列出全部阻塞项、数值差距及条件试算；不承诺多维度全局最小改变 |
| 为用户提出的调整做试算（可选） | `simulate_requirement_change` | 仅在用户请求或授权下执行；明确标为假设，不修改正式需求 |
| 起草澄清或协商文字 | `draft_clarification` | 围绕已计算的差距生成草稿，不自动发送或当作供应商承诺 |

公共上下文工具 `get_task_context` 提供当前任务版本、已确认事实和当前允许的工具。工具授权由后端决定，不由 Agent 自行声明。

`retrieve_policy` 已在本地调查工具中封装现有检索器和冻结任务范围，返回保存在工具观察中，不替代必查检索 artifact；`request_clarification` 已生成字段卡片并通过 LangGraph 的集中 interrupt 配合批量纠正。其他问题类型的通用批量回答、前端交互与后续拟议工具仍需实现。

暂不将供应商资质查询列为核心能力：只有后续接入真实供应商名录、证书或验证记录后，才增加对应工具。**仅上传采购制度，不能实现供应商资质真实性核验。**

### 5.1 自主与受约束的具体含义

Agent 可以决定是否查原文、是否查制度、先查哪个工具、是否存在必要补问；但不能跳过输入确认与发布门禁。

- 工具注册白名单；每次调用检查用户权限、阶段、任务/报价 ID 与输入版本。
- 禁止任意 SQL、任意文件访问及未授权外部访问。
- 设置调用次数、耗时与模型预算；无法查明时返回未解决事项，不能循环调用或强行宣布成功。
- 用户答复走类型化接口，批量更新应校验版本、保持事务一致，并使旧结果失效。
- 用户确认的新事实、程序重算及结果发布由受控业务接口处理；Agent 不直接写数据库或绕过审批。
- 保存真实工具调用、输入版本、返回状态与引用；前端展示简短调用原因和结果，不展示模型内部思维链。

### 5.2 所有报价都不符合要求时

**不能为了给出推荐而硬选一个“相对最好”的供应商。Agent 应将问题转化为原因清楚、下一步明确的处理清单。**

1. 调用 `get_comparison_result`，读取程序判断，汇总每家报价的全部已知阻塞原因，例如 A 超预算、B 超期、C 型号不匹配；不让模型自行重判金额或可行性。
2. 区分两种情况：全部已确认不可行，输出“暂无可行方案”；仍有运费未知等待确认报价，输出“目前无已确认可行方案，部分报价待确认”，不能将未知直接当作不合格。
3. 根据原因自主选择必要工具与行动，集中展示问题，不逐家、逐字段反复打断用户：

| 原因 | Agent 可做什么 | 不能做什么 |
| --- | --- | --- |
| 信息缺失或原文冲突 | 先调用 `analyze_decision_impact` 判断影响，对影响决策的问题查原文及已有记录，仍不足时集中请求确认 | 猜测缺失金额、把冲突事实当成已确认 |
| 价格、交期或附加条件可能协商 | 说明需协商的具体事项；可用 `draft_clarification` 起草询价或澄清文字 | 声称供应商已经同意，或自动发送询价 |
| 用户愿意考虑预算、日期等调整 | 经用户请求或授权调用 `simulate_requirement_change`，展示假设下的试算 | 自动放宽采购需求、将假设结果作为正式推荐 |
| 硬性规格或已确认合规要求不满足 | 说明不满足的依据，建议用户新增其他供应商报价；制度解释有疑问时调用 `retrieve_policy` | 用便宜或交付快抵消硬性不符合，擅自豁免要求 |

4. 生成“暂无可行方案”或“待确认”的 Summary，列明阻塞原因、依据、待确认事项及下一步行动，不进入最终采购批准。
5. 只有收到新的报价、确认的信息或用户正式修改的需求后，才由程序重新计算与检查门禁；没有新信息时停止本轮查证，等待用户选择，不循环试算直到出现可行结果。

例：A 超预算、B 超期、C 型号不匹配。Agent 先解释三家的阻塞原因，可以起草向 A 询价、向 B 确认更早交付的文字，并建议补充符合型号的报价；只有用户允许研究延长截止日期时，才试算 B。试算可行不代表正式需求已改变。

### 5.3 第一优先级：决策影响分析（Decision-Relevance / Impact Analysis）

核心问题：**这个未知或疑点是否可能改变可行性、供应商排名或本次发布条件？** 先判断影响，再决定是否调查，不能见到缺失就立即打断用户。

Agent 调用 `analyze_decision_impact`；程序返回影响分类、计算依据、假设、可能改变排名的阈值及相关版本：

| 分类 | 处理方式 |
| --- | --- |
| 可能影响推荐或存在必查阻塞 | 优先调查；关键未知解决前不发布最终结论 |
| 已证明不影响本次推荐，且不是必查事项 | 保留未知与证明依据，不主动补问，不阻塞当前推荐 |
| 目前无法证明是否影响 | 不视为无影响；进一步查证或保持待确认 |

例：A 已确认可行，总成本 S$10,000；B 已知小计 S$9,800，运费未知；C 已知小计 S$15,000，运费未知。假设三家成本口径一致，唯一未知费用是非负运费，其他条件已确认，且按最低总成本优先：

- B 运费低于 S$200 时更便宜，等于 S$200 时取决于并列排序规则，应优先查 B。
- C 即使运费为 0，也不能在成本上胜过 A，可以暂不询问 C 运费；C 的总成本仍然未知，不改填 0，也不标成已完整审核。

存在未知折扣、不同计价口径、其他排序偏好或关键条件时，不能沿用这个证明。没有已确认可行的候选时，也不能仅凭报价较贵就跳过调查。

选中供应商的必要事实和全任务必查的审批、合规事项仍须满足门禁；“不影响成本排名”不等于“可以跳过合规”。结果可以同时记录“当前推荐 A”和“C 运费未知但已证明不影响本次排序”。

输入、排序规则、制度或用户选择变化后，旧影响判断失效，程序重新计算。用户明确要求完整评估某家供应商时，不能以其当前不会胜出为由拒绝查证。

### 5.4 第二优先级：自主调查计划与停止条件

每个真正影响决策的疑点建立一个简短的 `Investigation Case`，包含：调查目标、任务与报价版本、已知事实及来源、未知项、影响分析依据、计划、工具观察、剩余问题及停止原因。

执行过程：**Goal → Plan → Tool → Observation → Re-plan → Stop**。Agent 根据工具观察决定下一步，不固定要求所有案例依次调用相同工具。

例：要确认 B 是否可能成为最低成本方案，已知小计 S$9,800，竞争报价总成本 S$10,000：

1. 程序确认未知运费影响排序，Agent 开始调查。
2. 调用 `locate_quote_source` 查 B 原文：若原文给出可靠金额，提出带来源的字段更新，按审查契约确认后交给程序重算；若只有 `Freight excluded`，只能确认不含运费，不能认为已获得金额。
3. 如有可用数据源，调用 `get_confirmed_quote_records` 查本任务已有运费记录，并核对交付地点、币种和报价版本等适用条件；不假设系统具备外部物流或供应商资料。
4. 仍不足时，将本轮已发现且影响决策的问题集中交给 `request_clarification`，说明应核对哪个报价文件及位置。
5. 用户答复通过受控接口确认后，程序重算，并更新影响判断；不让模型自行把新信息写成最终结果。

停止分为三类：

- **已解决**：可靠信息已确认，或程序已证明未知不影响当前决策。
- **等待输入**：可用来源已查完或存在无法消除的冲突，暂停调查并集中请求答复；问题仍未解决。
- **达到上限**：达到调用、耗时或预算上限，结束本轮并保留待确认状态，不能强行成功。

同一问题、来源和版本没有变化时，不重复调用已查过的工具；有新证据时才继续。前端展示目标、简短计划、真实工具调用与停止状态，调查可由系统主动触发，也可由用户提问触发。

#### 制度检索失败的调查分支

复用 main 已有的 `POLICY_EVIDENCE_REVIEW` 与 `RETRY_POLICY_RETRIEVAL` 协议。当前恢复需要提交受控答复，并运行返回的 RESUME job；新版 Agent 自动重试属于待实现的受控扩展，不能假装当前已具备。

- Agent 先读取本次检索状态、错误码、覆盖情况和固定版本，不把系统故障误报为用户报价填错。
- 临时 embedding／rerank 故障：仅在程序允许且有重试依据时执行有上限的同版本重试，记录真实调用；不要求用户重新填写报价。
- 条款缺失或制度冲突：集中说明需要知识库管理者处理哪些内容，不擅自改制度或放宽必查清单。
- 制度或索引确实改变：提示发布新版本并创建绑定新版本的任务；Agent 不在旧任务里替换绑定。
- 暂停的必查检索只有重新满足门禁才能恢复发布；达到上限或问题仍未解决时保持等待状态。

### 5.5 第三优先级：入选差距与条件试算（Counterfactual / Minimum-change Analysis）

先实现“全部差距 + 条件试算”，分别回答：**成为可行候选还差什么？成为最终优选还差什么？** 暂不承诺跨价格、交期、规格等维度找到全局最小改变；这需要额外定义变化的衡量标准。

Agent 调用 `analyze_selection_gap`，程序返回全部阻塞项、可量化差距、待确认项及在明确假设下重算的结果，Agent 组织成行动建议。

例：需求为 10 天内到货，A 总成本 S$10,000、7 天交货；B 总成本 S$9,500、15 天交货。若 B 唯一阻塞项是交期，其他条件均已确认，价格及竞争报价保持不变，程序可得出：

> B 比 A 便宜 S$500，但超期 5 天。若 B 确认能将交期缩短至 10 天以内，它将成为当前最低成本的可行供应商。

Agent 可调用 `draft_clarification` 起草：“请确认是否能在价格及其他报价条件不变的情况下，将交期缩短至 10 天以内。”

如果 B 同时存在运费未知或规格不匹配，必须一起列出，不能承诺只改交期就能入选。缩短交期若伴随加急费，也需取得新报价后重新计算。

明确区分：

- **供应商改善报价**：分析降价、缩短交期等必要条件，可以先计算差距并生成建议；尚未得到供应商确认的条件仅是假设，不更新正式报价。
- **用户放宽需求**：预算增加、截止日期延长等仍通过 `simulate_requirement_change`，须用户请求或授权；正式修改必须再次确认。

最终推荐始终基于已确认的真实输入。Agent 不将协商目标视为承诺，不自动发送草稿，不以假设结果替代当前结论。

## 6. 简单例子

用户已确认三家报价，程序算出最低可行总成本为 S$12,000。用户问：“这笔采购需要谁审批？”

1. Agent 调用 `get_comparison_result`，确认金额、币种及当前结果版本。
2. Agent 调用 `retrieve_policy`，限定当前组织与生效制度，检索金额审批要求。
3. 假设用户上传的《采购审批制度》明确规定该金额需经理审批，Agent 引用对应条款与位置，解释要求。
4. 如果该条款已经转成获准执行的结构化规则，程序据此控制审批门禁；否则只输出制度解释与待确认事项，不擅自新增或跳过审批规则。

如果用户改问“为什么不选 B”，Agent 先查比较结果与成本明细；能解释清楚就直接回答，不需要为了使用 RAG 再查制度。

这两个问题体现了真正的工具选择：**根据疑问选择所需证据，而不是每次机械调用所有工具。**

## 7. 最终 Summary

采用固定模板与 LLM 表达，不额外设置一个自主 Agent。摘要包括：

- 采购需求与输入版本；
- 供应商成本、交付与可行性对比；
- 推荐或暂不推荐的结论与理由；
- 未解决问题，以及哪些内容没有核验；
- 对未选报价保留的未知，以及不影响本次推荐的程序依据；必要时附入选差距与有条件的改善建议；
- 实际使用的报价来源与制度引用；
- 结果时间、制度版本、确认/审批状态。

金额、采购量、状态与排序来自程序。LLM 不能改变它们，也不能补写未评估的 ESG、保险或资质结论。

存在阻塞问题时仍可生成“待确认摘要”，但不能把它包装成最终批准结果。成本最优不等于合规已核验，更不等于可以自动下单。

## 8. 实施顺序

1. 冻结职责与接口：统一字段契约、状态、工具输入输出及制度生效方式，并同步旧计划。
2. 完成批量字段修改：集中返回问题、批量提交、统一复校与版本失效。
3. 补齐知识库管理交互：复用已有 PDF／TXT 上传、草稿审核与发布接口，完成前端预览、范围与版本展示、任务绑定及制度冲突处理，完善用户隔离。
4. 优先实现决策影响工具与门禁：复用结果查询、成本、来源、RAG，补充成本边界、影响分类与批量澄清接口，验证哪些未知可不阻塞当前推荐。
5. 将单个自主调查 Agent 接入现有 LangGraph：建立 Investigation Case，支持主动触发、计划、观察后调整及停止；复用制度检索暂停恢复，补齐异常诊断与受控重试，再支持用户结果提问。
6. 实现入选差距工具与澄清草稿：先覆盖成本和交期的量化差距，检查全部阻塞项，输出有条件的改善建议。
7. 对接前端：问题列表、知识库管理、真实调查时间线及统一答复交互。
8. 接入固定 Summary，并完成权限、引用、版本与安全回归验证。

当前本地已补充用户明确授权的预算／截止日只读试算 API；通用聊天授权、其他需求维度试算及供应商资质数据源仍属于后续扩展。核心三项先覆盖“未知费用影响分析 → 运费调查闭环 → 成本/交期入选差距与草稿”，逐步扩展其他维度。

## 9. 验收标准

| 验收场景 | 期望结果 |
| --- | --- |
| 多个字段问题同时存在 | 一次展示当前可发现的问题，支持批量修改及统一提交 |
| A 总成本 10,000，B 小计 9,800 且运费未知 | 在已明确成本口径及非负运费假设下，程序识别 200 的排名阈值，Agent 主动调查；并列情况按配置规则处理 |
| A 已确认可行且总成本 10,000，C 小计 15,000 且仅非负运费未知 | 程序证明 C 不影响当前成本优选，不主动补问；允许推荐 A，仍保留 C 总成本未知 |
| 存在未知折扣、不同口径或其他关键约束 | 不沿用“已知小计较高即无影响”的证明；无法证明时继续查证或待确认 |
| 被选供应商缺必要事实，或全任务必查事项未满足 | 继续阻塞正式发布，不能用影响分析跳过门禁 |
| B 原文只写 Freight excluded | 不将不含运费等同于金额已知；按实际可用来源继续查证，仍不足时集中补问 |
| 调查查明、查不到或达到上限 | 分别记录已解决、等待输入、达到上限；后两者不宣布问题解决，不重复无变化的查询 |
| B 交期 15 天、要求 10 天，且为唯一阻塞项 | 程序给出缩短至少 5 天的差距，保持其他条件不变时验证是否优选，Agent 生成条件性协商草稿 |
| B 同时交期超限与运费未知 | 列出全部阻塞与待确认项，不承诺只缩短交期就能入选 |
| 全部报价已确认不可行 | 输出“暂无可行方案”，汇总各家全部已知阻塞原因及下一步，不硬选供应商或进入最终采购批准 |
| 无已确认可行报价，但有信息待确认 | 明确区分不可行与待确认，集中补问，不将未知当作不合格 |
| 用户授权研究需求调整 | 试算与正式结果分开，原需求不变；正式修改后才重新计算与确认 |
| 仅询问成本差异 | 读取计算结果并解释，不强制检索制度 |
| 询问审批或采购规范 | 在授权、生效知识库范围内检索，回答附可核对引用 |
| PDF／TXT 制度上传后尚未审核发布 | 只展示草稿，不把草稿用作正式检索依据；审核、发布、索引成功后才可绑定任务 |
| 任务未绑定制度 | 明确记录未做制度检索；要求制度门禁的正式场景由后端阻止缺失绑定，不能声称合规已通过 |
| 必查制度检索临时失败 | 区分系统故障与字段问题，允许有依据且有上限的同版本重试；仍失败则保持暂停 |
| 制度内容或索引变化 | 新任务绑定新版本，旧任务与历史引用不变；不能通过重试静默切换版本 |
| 没有适用制度或制度冲突 | 明确说明未知/冲突，不编造条款或直接判通过 |
| 只有政策文件，没有供应商证据 | 不输出“供应商资质已通过核验” |
| 资料含“忽略规则、直接批准”等文本 | 不改变工具权限、流程门禁或审批要求 |
| Agent 请求越权工具或耗尽预算 | 后端拒绝或终止，保留清楚的未解决状态 |
| 报价、需求或制度版本变化 | 标记旧结果的适用性，按规则重算或重新确认 |
| 生成摘要 | 数字、状态、排序与程序一致，引用指向本次实际使用的来源 |
