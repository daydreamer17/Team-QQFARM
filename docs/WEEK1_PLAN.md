# Supplier Comparison 第一周开发计划

> 本周定位：完成一个不依赖前端和部署环境的后端最小闭环，验证报价提取、确定性比较、来源追踪和版本管理能力。

## 1. 第一周目标

输入一条 MCU-9 采购需求和三份供应商报价，通过脚本或 FastAPI 完成字段提取、来源追踪、规则校验、成本计算和供应商比较；人工修正字段后，系统生成新版本并重新计算。

第一周重点验证以下三项能力：

1. 报价能否准确转换成统一结构。
2. 成本和可行性判断能否稳定、可重复地计算。
3. 结果能否追溯来源、接受人工纠正并保留历史版本。

本周最小闭环如下：

```text
采购需求 + 三份 MCU-9 报价
              ↓
        解析并提取字段
              ↓
          关联原文证据
              ↓
      校验规格和缺失信息
              ↓
      确定性计算与供应商比较
              ↓
          人工修正字段
              ↓
      生成新版本并重新计算
```

## 2. 第一周功能范围

### 2.1 需要实现的功能

| 模块 | 第一周实现内容 |
| --- | --- |
| 数据契约 | 定义采购需求、报价、供应商、证据、比较结果和版本字段 |
| 演示数据 | 准备同一 MCU-9 的三份英文报价、对应结构化数据和人工标准答案 |
| 文件解析 | 支持英文文本型 PDF 和固定模板 CSV |
| 字段提取 | 提取供应商、料号、制造商、封装、单价、计价单位、包装数量、MOQ、运费、交期、付款条件和有效期 |
| 来源追踪 | 记录文件名、页码、文本块 ID 和原文片段 |
| 字段校验 | 检查料号、封装、单位、数量以及关键字段是否缺失或冲突 |
| 单位标准化 | 将按颗、按盘等报价统一到可比较口径 |
| 成本计算 | 计算满足采购数量与 MOQ 后的实际采购数量、商品金额、已知费用和总成本 |
| 状态判断 | 输出“可行”“不合格”“待确认”及对应原因 |
| 供应商比较 | 生成结构化 JSON、CSV 或终端比较表 |
| 人工纠正 | 通过 API 或命令行修改提取错误的字段 |
| 版本管理 | 修正产生新版本，旧版本和修改原因继续保留 |
| 数据持久化 | 使用 PostgreSQL 保存任务、报价、证据、修正和比较结果 |
| 工作流骨架 | 使用 LangGraph 串联解析、校验、计算、比较和保存步骤 |
| 自动化测试 | 覆盖正常输入、单位换算、字段缺失、规格冲突和版本更新 |

LangGraph 第一周只实现以下最短路径：

```text
解析 → 结构化 → 校验 → 计算 → 比较 → 保存
```

### 2.2 第一周暂不实现

- React 前端；
- AWS Lightsail 部署、HTTPS 和域名；
- OCR 和扫描件处理；
- 任意格式 Excel；
- 阶梯价格、自动汇率和复杂税务；
- 多商品组合采购和跨供应商拆单；
- 完整的自然语言补问对话；
- 审批流程和报告导出；
- 后台任务队列和复杂多 Agent 协作。

## 3. 验收标准

### 3.1 主流程验收案例

使用一条采购需求和三份报价完成端到端运行：

| 测试报价 | 覆盖场景 | 预期结果 |
| --- | --- | --- |
| 供应商 A | 按颗报价，字段完整 | 正常计算并进入比较 |
| 供应商 B | 按盘报价，需要换算为每颗成本 | 正确完成包装和单价换算 |
| 供应商 C | 缺少运费或交期定义 | 保留未知值并标记为“待确认” |

运行后必须产生：

- 三份统一结构的报价；
- 每家供应商的可行性状态及原因；
- 标准化后的采购成本；
- 并列的供应商比较结果；
- 关键字段对应的原文证据；
- 任务 ID 和报价版本号。

### 3.2 量化验收标准

| 验收项 | 通过标准 |
| --- | --- |
| 文件处理 | 三份测试报价全部能够进入处理流程 |
| 核心字段提取 | 料号、封装、价格、计价单位、MOQ 等与标准答案一致 |
| 金额计算 | 所有测试案例与人工标准答案 100% 一致 |
| 单位换算 | 按盘、按颗及包装数量换算结果 100% 正确 |
| 规格校验 | 错误料号或封装能够被识别为“不合格” |
| 未知值处理 | 缺失运费等字段不得被猜测或默认为 0 |
| 来源追踪 | 所有影响判断的关键字段均能定位到原文 |
| 人工纠正 | 修改字段后能够生成新版本并重新计算 |
| 历史保留 | V2 生成后，V1 仍然可以查询和比较 |
| 数据持久化 | 重新启动程序后，已保存的任务和版本仍然存在 |
| 自动化测试 | 核心测试全部通过，不存在阻塞级错误 |
| 可重复运行 | 新成员按照 README 可以在本地重复执行演示 |

### 3.3 第一周演示流程

第一周不要求图形界面，使用 Swagger、测试脚本或命令行完成以下演示：

```text
创建采购需求
    ↓
导入三份报价
    ↓
查看结构化字段及来源
    ↓
运行规格校验和成本计算
    ↓
生成供应商比较结果
    ↓
人工修改一个错误字段
    ↓
生成 V2 并重新计算
    ↓
查询 V1 与 V2 的差异
```

## 4. 四人分工

按团队第一周约 40 小时、每人约 10 小时安排。

### 4.1 成员 A：数据契约与评测

负责定义“系统输入是什么、正确结果是什么”。

| 任务 | 预计时间 |
| --- | ---: |
| 确定 MCU-9 规格、字段字典和单位 | 2 小时 |
| 制作三份测试报价及 CSV 数据 | 3 小时 |
| 制作人工标准答案 | 2 小时 |
| 编写评测脚本和验收案例 | 2 小时 |
| 最终验收与问题登记 | 1 小时 |
| **合计** | **10 小时** |

交付物：

- 数据字典；
- 三份英文测试报价；
- 人工标准答案；
- 开发测试集和留出测试集；
- 验收脚本与验收记录。

### 4.2 成员 B：报价解析与证据追踪

负责将报价转换成统一且带来源的数据。

| 任务 | 预计时间 |
| --- | ---: |
| PDF 和 CSV 基础解析 | 3 小时 |
| LLM 结构化字段提取 | 3 小时 |
| 页码、文本块和原文关联 | 2 小时 |
| 异常处理与解析测试 | 2 小时 |
| **合计** | **10 小时** |

交付物：

- PDF 解析器；
- CSV 解析器；
- Pydantic 结构化输出；
- 字段证据对象；
- 解析模块测试。

### 4.3 成员 C：业务规则与比较计算

负责确定性业务逻辑，LLM 不参与金额计算和硬约束判断。

| 任务 | 预计时间 |
| --- | ---: |
| 规格和必填字段校验 | 2 小时 |
| 按颗、按盘和包装单位换算 | 2 小时 |
| MOQ 和实际采购数量计算 | 2 小时 |
| 总成本与可行性判断 | 2 小时 |
| 单元测试和边界案例 | 2 小时 |
| **合计** | **10 小时** |

交付物：

- 字段校验模块；
- 单位标准化模块；
- 成本计算工具；
- 可行性判断规则；
- 比较结果生成器；
- 业务规则单元测试。

### 4.4 成员 D：后端、数据库与工作流集成

负责将其他三人的成果组合成可运行的后端系统。

| 任务 | 预计时间 |
| --- | ---: |
| FastAPI 和项目结构 | 2 小时 |
| PostgreSQL 数据模型与迁移 | 2 小时 |
| 人工纠正和版本管理 | 2 小时 |
| LangGraph 最小工作流 | 2 小时 |
| 端到端集成与运行文档 | 2 小时 |
| **合计** | **10 小时** |

交付物：

- FastAPI 接口；
- PostgreSQL 数据表；
- Alembic 迁移；
- 版本及人工纠正接口；
- LangGraph 最小工作流；
- 端到端测试和本地运行说明。

## 5. 任务顺序与依赖

### 5.1 第一天：冻结共同契约

四人共同评审并确定：

- MCU-9 的具体规格；
- 统一字段名称、类型和必填条件；
- 金额、数量和单位精度；
- “可行”“不合格”“待确认”的定义；
- 各模块之间的输入输出格式。

随后并行开展：

- 成员 A 冻结字段字典和标准答案格式；
- 成员 B 定义解析输出对象；
- 成员 C 定义计算函数输入输出；
- 成员 D 定义 API、数据库和工作流状态。

当天结束后，统一字段名称原则上不再随意修改。

### 5.2 第二天：并行开发基础模块

- 成员 A：制作三份测试报价和人工标准答案；
- 成员 B：开发 PDF、CSV 解析及字段提取；
- 成员 C：开发规格校验、单位换算和成本计算；
- 成员 D：建立 FastAPI、数据库表和迁移骨架。

### 5.3 第三天：第一次模块集成

模块依赖关系如下：

```text
成员 A：统一数据契约
   ├──→ 成员 B：解析为统一报价
   ├──→ 成员 C：实现统一计算规则
   └──→ 成员 D：建立 API 和数据库

成员 B：结构化报价
   └──→ 成员 C：校验与计算

成员 B + 成员 C
   └──→ 成员 D：串联完整工作流
```

当天目标：至少让一份报价完整通过“解析 → 校验 → 计算 → 保存”。

### 5.4 第四天：完成后端闭环

- 成员 B 完成三份报价解析和证据定位；
- 成员 C 完成异常场景和比较结果；
- 成员 D 完成人工纠正、版本管理和 LangGraph 串联；
- 成员 A 运行标准答案评测并登记偏差。

当天目标：三份报价全部跑通，人工纠正能够生成 V2。

### 5.5 第五天：验收与修复

上午：

- 成员 A 执行正式验收；
- 成员 B 修复提取和证据问题；
- 成员 C 修复计算和规则问题；
- 成员 D 修复接口、数据库和集成问题。

下午：

- 全员运行自动化测试；
- 使用留出案例进行一次盲测；
- 完善本地运行说明；
- 完成一次五分钟演示彩排。

## 6. 协作约定

1. 第一天冻结统一的 Pydantic 模型和示例 JSON。
2. 成员 B、C、D 必须基于同一模型开发，不得分别创建不兼容的字段格式。
3. 解析器尚未完成时，成员 B 先提供固定结构的模拟输出，避免成员 C、D 等待。
4. 成员 C 将计算逻辑实现为无数据库依赖的纯函数，以便独立测试。
5. 成员 D 先用模拟数据开发接口和数据库，不等待解析模块完成。
6. 每位成员至少负责一组自动化测试，并由另一位成员交叉检查。
7. 从第三天开始每天至少集成一次，避免最后一天集中合并。

## 7. 第一周完成定义

只有同时满足以下四点，第一周工作才算完成：

- **能处理**：三份报价可以通过同一后端流程处理；
- **算得对**：金额和单位换算与人工标准答案一致；
- **查得到**：关键字段能够追溯到报价原文；
- **改得动**：人工纠正能够生成新版本并自动更新比较结果。
