# 数据字典拆分更新记录

版本：1.2.0

日期：2026-09-09

范围：供应商报价、采购需求、系统与证据字段

## 1. 本次更新

本轮把原先混合在一份宽表中的字段，按实际业务对象拆分为三份数据字典：

| 文件 | 字段数 | 用途 |
| --- | ---: | --- |
| `quote_data_field.csv` | 31 | 定义供应商报价中的身份、规格、价格、包装、MOQ、费用、交期和商务字段 |
| `procurement_requirement_fields.csv` | 19 | 定义采购人员提交的产品要求、数量、预算、交付要求和比较偏好 |
| `system_evidence_fields.csv` | 29 | 定义任务、报价、文件、字段候选、核验、来源、快照、规则版本和测试溯源 |

三份文件统一使用与“精简”表相同的 19 列结构：

`field_name`、`type`、`meaning`、`example`、`字段组`、`必填级别`、`缺失处理`、`常见别名或表达`、`统一表达规则`、`校验与歧义边界`、`证据要求`、两份原始 CSV 的同名列标记、`对应原始列`、`本次值来源分类`、`来源说明`、`责任方`、`适用范围`和`字典版本`。

本轮不修改三家演示供应商的报价数值、采购需求数值、参考答案和确定性计算规则，也不表示相关解析、Pydantic、持久化或审批功能已经完成。

## 2. 主要完成内容

### 2.1 供应商报价数据字典

`quote_data_field.csv` 保留已确认的“精简”版本，共 31 个字段，不再继续删除或改名。

字段分为：

- 身份：供应商编号、名称和国家。
- 规格：类别、商品描述、制造商、制造商料号、封装、版本和产品状态。
- 价格：币种、单价、价格基数数量和价格基数单位。
- 包装与 MOQ：销售包装、每包数量、订购步长、最低起订量及其单位。
- 费用：运费状态与金额、其他费用状态与金额、税费口径。
- 交期：交期天数、自然日/工作日、发货/到货语义和起算事件。
- 商务：付款条件、报价日期和有效期。

该字典是 B 处理供应商 PDF/CSV 时的业务字段目标。标为“系统”的字段仍由后端提供，不要求模型从报价文件中猜测。

### 2.2 采购需求数据字典

`procurement_requirement_fields.csv` 新增 19 个字段：

- 产品 7 项：制造商、制造商料号、封装、版本、产品状态、是否允许替代、基础单位。
- 数量 2 项：需求数量、数量单位。
- 预算 5 项：预算金额、币种、是否包含运费、税费口径、是否要求其他费用完整。
- 交付 3 项：计划下单日期、最迟到货日期、收货地点。
- 比较偏好 2 项：首要排序偏好、次要排序偏好。

采购需求来自采购人员填写或明确确认，不从供应商报价、历史采购订单或多数供应商的共同值反向补齐。当前演示值属于团队合成数据；真实运行时应记录为用户输入或批准的系统配置。

### 2.3 系统与证据数据字典

`system_evidence_fields.csv` 新增 29 个字段，覆盖：

- 结构、任务、报价和文件身份及版本。
- 文件 SHA-256、解析器版本和字段版本。
- `raw_value`、`normalized_value`、`unit` 等字段候选。
- `validation_status`、`origin`、`source_refs` 和核验记录。
- 不可变输入快照、计算规则版本及预留的制度集合版本。
- `fees_complete` 等确定性校验结果。
- `scenario_id`、`supplier_alias`、`source_po_id`、`is_synthetic` 等测试与数据治理信息。

这些字段不计入供应商报价字段准确率。任务与版本由 D 管理；文档解析和来源由 B 生成；确定性规则和费用完整性由 C 判断；A 负责字段业务定义、样例和验收口径。

## 3. 实现思路

### 3.1 按数据归属拆分

三个对象分别回答不同问题：

| 对象 | 回答的问题 |
| --- | --- |
| 采购需求 | 买方要买什么、数量和预算是多少、何时必须到货 |
| 供应商报价 | 供应商实际提供什么、如何计价、有什么订购和交付条件 |
| 系统与证据 | 数据属于哪个任务和版本、来自哪里、是否已经核验 |

采购需求与供应商报价中的同名字段具有不同含义。例如采购需求的 `manufacturer` 是目标制造商，报价中的 `manufacturer` 是供应商声称提供的制造商。后续模型应通过对象路径区分，C 再执行规格一致性检查，不允许一个值覆盖另一个值。

### 3.2 保留原文与标准化候选

B 对报价文件的处理顺序为：

1. 保存原始文本或单元格内容到 `raw_value`。
2. 按供应商报价字典匹配字段和别名。
3. 生成 `normalized_value` 候选并保留单位。
4. 关联本次文件允许的 `source_refs`。
5. 先标记为 `EXTRACTED`；通过来源、单位、范围、跨字段和语义检查后才能成为 `VERIFIED`。

结构合法不等于字段已经核验。缺失字段不能借用采购需求、历史订单、示例值或其他供应商的值补齐。

### 3.3 将业务字段与运行控制分开

`task_id`、`task_revision`、`quote_version`、`document_sha256` 等等由后端附加，不让模型从文件内容中生成。这样可以防止新版需求使用旧报价结果，也能验证引用是否真正属于当前文件和版本。

`fees_complete` 是 C 根据运费、其他费用、税费口径和未解决问题得出的结果，不是供应商报价原文。

### 3.4 保持现有模块边界

- A：维护数据字典、样例、来源说明、独立参考答案和业务验收。
- B：解析 PDF/CSV、输出字段候选、来源位置和模型调用记录。
- C：执行数量、MOQ、费用、日期和可行性规则。
- D：维护任务、版本、快照、问题、作业、持久化和审批。

数据字典描述共享含义，但不复制 C 的计算公式，也不替代 D 的状态与版本逻辑。

## 4. 相比上一版的变化

上一种组织方式把 41 个报价业务字段、系统字段、测试字段和共同采购上下文放在同一张表中。字段定义虽然完整，但容易出现以下问题：

- B 不容易判断哪些值应从报价中提取，哪些值应由后端提供。
- 采购需求和供应商报价的同名字段可能被当成同一个值。
- 系统版本、来源证据和业务报价混在一起，字段准确率口径不清楚。
- 继续增加 Week 2 的制度、问题和审批字段时，报价表会不断变宽。

本轮改为：

| 上一组织方式 | 本轮组织方式 |
| --- | --- |
| 一份宽表混合多种数据 | 三份字典按数据对象分开 |
| 报价字段与系统字段混合 | 报价 31 项，系统与证据 29 项 |
| 采购需求只存在于样例 JSON 或说明中 | 采购需求形成独立的 19 字段字典 |
| 缺失处理容易被理解成强制填满 | 按关键、条件关键、可选和系统分别处理 |
| 来源列只说明字段来自哪里 | 同时区分运行时原文、标准化候选、核验状态和来源引用 |

供应商报价的“精简”版本已经由负责人确认，因此本轮不再删改其中 31 项。采购需求和系统字段使用相同的列结构，便于团队审阅和后续生成共享模型。

## 5. 修改原因

1. **减少错误补值。** 历史订单、采购需求和其他供应商的内容不能填补当前报价缺失项。
2. **区分未知与零。** 运费空白不是免费，其他费用未说明也不是明确为零。
3. **保护版本正确性。** 需求、报价或人工确认变化后，旧结果和审批不能继续作为当前结论。
4. **支持证据核验。** PDF 需要页码、文本块和可用坐标；CSV 需要记录行号和列名。
5. **方便分工。** A、B、C、D 可以按同一字段含义开发，而不重复建立第二套模型。
6. **控制后续扩张。** Week 2 的 RAG、问题、审批和报告记录不继续塞进供应商报价字段。

## 6. 使用方法

### 6.1 A：数据与验收

- 用三份字典检查字段名称、含义、必填级别、示例和来源分类。
- 修改共享字段时同步检查 `docs/WEEK1_PLAN.md`、`docs/ARCHITECTURE.md`、`docs/DATA.md` 及主演示答案。
- 示例值只用于说明，不能成为字段缺失时的默认值。
- 评测时分别统计金额、计价单位、包装、MOQ、费用和交期，不把系统字段计入提取准确率。

### 6.2 B：解析与模型适配

- 只从 `quote_data_field.csv` 选择标准报价字段。
- 保存原始值和来源，再生成标准化候选。
- 模型只能引用当前解析提供的来源 ID。
- 缺失值标记为 `MISSING`；矛盾值标记为 `CONFLICT`；不得伪造引用。
- `scenario_id`、`quote_id`、`document_id` 等由系统上下文提供，不从报价正文猜测。

### 6.3 C：确定性业务规则

- 从采购需求读取数量、预算、截止日期和比较偏好。
- 从已核验报价读取价格基数、包装、MOQ、费用和交期。
- 使用 Decimal/NUMERIC 处理金额。
- 未知费用不按零计算；存在可能影响选择的未解决报价时保持 `PENDING`。
- 计算结果关联 `snapshot_id` 和 `calculation_rule_version`。

### 6.4 D：API、版本和持久化

- 创建并校验 `task_id`、`task_revision`、报价、文件和字段版本。
- 将采购需求、报价候选、来源、问题和结果分别保存。
- 输入变化创建新修订和不可变快照，拒绝旧作业覆盖当前结果。
- Week 2 接入 RAG 时使用 `policy_set_version`，检索轨迹另存，不修改报价业务字段。

### 6.5 缺失值与确认

- “关键”表示字段可能直接影响规格、成本、预算、交期或最终选择。
- 关键字段缺失且仍可能影响选择时，系统创建待确认问题，由采购人员通过结构化表单或 API 补充。
- 系统不自动联系供应商。采购人员可在系统外核实，再提交明确答案。
- 明确“无偏好”是有效答案。次要偏好可保存为 `null` 并继续；它与尚未回答不同，确认记录应保存在系统证据中。
- 已有可靠硬约束失败或被用户明确排除的报价，不需要为了排除结论继续追问无关缺失字段。

## 7. 版本与变更规则

- 三份字典当前版本均为 `1.2.0`。
- 字典版本用于说明字段定义，不等于业务 JSON 的 `schema_version`。
- 修改说明、别名或示例但不改变接口，可更新字典说明版本。
- 修改 `field_name`、类型、枚举、金额口径、日期语义或必填行为，可能影响 B/C/D 接口，必须由团队确认并同步样例、参考答案和测试。
- Week 1 正式输入范围仍是一种英文文本 PDF 开发版式、固定 CSV 模板和一份独立版式的小规模留出输入；字典中的现实别名不代表所有格式已经实现。

## 9. 当前边界

本轮交付的是字段定义和使用约定，不是解析器、规则层、API、数据库、RAG 或审批功能的完成证明。模拟候选不能冒充真实模型输出，本地结果不能冒充 AWS 或主办方 API 验收结果。系统最终输出的是采购建议及审批记录，不是采购订单，也不会自动签约、下单或付款。
